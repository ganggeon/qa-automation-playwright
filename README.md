# SW QA 학습 & 포트폴리오

테스트 설계 기법으로 케이스를 도출하고, API·UI 자동화로 검증하고,
그 결과를 QA 산출물로 전달하는 전 과정을 담은 프로젝트입니다.

| | |
|---|---|
| **테스트 수행** | 176건 (API 91 · UI 20×3브라우저 · 외부 24 · 초기화 1) |
| **검출 결함** | 21건 (자체 SUT 16 + 외부 공개 API 5) |
| **적용 기법** | 동등분할 · 경계값 분석 · 결정표 · 상태 전이 · 오류 추정 |
| **기술 스택** | Playwright(TypeScript) · Postman/Newman · Ajv · GitHub Actions |
| **실행 시간** | 전체 약 50초(벽시계) / Fail 0 |

---

## 이 프로젝트의 구조

```
요구사항 명세(SPEC.md)          ← 테스트 설계의 유일한 기준
        │
        ├─▶ 테스트 계획서
        ├─▶ 설계 기법 적용 → 테스트케이스
        │        │
        │        ├─▶ API 자동화 (Playwright)
        │        ├─▶ UI 자동화 (Playwright + POM)
        │        └─▶ Postman 컬렉션
        │                 │
        │                 ▼
        │            테스트 수행
        │                 │
        └─────────▶ 결함 리포트 → 요약 보고서 → 릴리스 판단
```

**핵심 원칙: 테스트는 코드가 아니라 명세를 보고 설계했다.**
구현을 보고 만들면 "구현이 틀린 경우"를 영원히 못 잡는다.

```bash

npm run report    # HTML 리포트 열기
```

## 대표 사례 4가지

### 1. 정답지에도 없던 결함 — "명세를 규칙 단위로 쪼개지 않으면 조건 하나를 놓친다"

FR-06-4는 "장바구니에 이미 있는 수량과 합산한다 + 합산 결과도 FR-06-2/3(수량 규칙)을 지켜야 한다"
두 조건이 한 문장에 있다. 요구사항 단위로만 커버리지를 세면 대응 TC가 있어 100%로 보이지만,
**규칙 단위**로 쪼개 보면 뒤 조건(합산 결과 검증)이 비어 있었다.

| 상황 | 기대 | 실제 |
|---|---|---|
| 담겨 있는 수량 60 + 추가 50 → 합계 110 (상한 100 초과) | 400 | 201 (담김) |

원인은 `BUG-016` — 수량 검증이 **요청값에만** 걸려 있고, 합산이 끝난 뒤의 **상태 변경 시점**에는
안 걸려 있었다. 이 결함은 SUT 제작자의 정답지(`SEEDED-DEFECTS.md`)에도 없던 것이다 —
명세만 보고 규칙 단위로 정독했을 때만 드러난, 자작 SUT의 100% 검출률에 대한 가장 설득력 있는 반례다.

### 2. 경계값 분석 — "네 점을 기계적으로 찍으면 한쪽이 비어 있다"

비밀번호 길이 8~20 규칙에 **min-1, min, max, max+1** 을 기계적으로 적용했다.

| 입력 | 위치 | 기대 | 실제 |
|---:|---|---|---|
| 7자 | min-1 | 400 | 400 ✅ |
| 8자 | min | 201 | 201 ✅ |
| 20자 | max | 201 | 201 ✅ |
| **21자** | **max+1** | **400** | **201 ❌** |

개발자는 `if (pw.length < 8)` 만 썼다. 세 점은 통과하고 네 번째에서 무너진다.

경계 계열 결함 6건을 실제로 분해해 보면 방향이 한쪽으로 쏠려 있지 않다.

| 유형 | 건수 | 결함 |
|---|---:|---|
| 상한 검증 누락 | 2 | 비밀번호 21자(BUG-001), 나이 121(BUG-002) |
| 하한 검증 누락·오류 | 3 | size 0(BUG-006), 수량 0·음수(BUG-008), 결제금액 0원 하한(BUG-013) |
| 비교 방향 오류(`≥`를 `>`로) | 1 | 쿠폰 최소금액(BUG-011) |

즉 **"상한만 빼먹는다"가 아니라 "어느 쪽이든 한쪽 끝을 빼먹는다"** 가 실제 패턴이다(6건 중 5건).
그래서 min·max 어느 한쪽만 확인하는 것은 의미가 없고, 네 점을 다 찍어야 한다.

> 위 표는 **결함의 성격**에 따른 분류다. **검출한 기법** 기준으로 세면 경계값 분석이
> 잡은 결함은 BUG-001·002·006·008·011·016 **6건**이다. 두 분류가 겹치지만 같지는 않다
> — 예를 들어 BUG-013(음수 결제금액)은 성격은 경계값이지만 실제로는 오류 추정으로 잡았다.

### 3. 결정표 + 경계값 — "이상(≥)을 초과(>)로 구현"

주문 기능의 조건 5개(2⁵ = 32조합)를 결정표로 **규칙 6개**로 압축해 전부 통과시켰다.
그런데 결정표는 조건의 Y/N만 본다. "주문금액 ≥ 최소금액"이 **정확히 같을 때** 어느 쪽인지는 안 본다.

경계값으로 정확히 30,000원 케이스를 추가하자 결함이 드러났다.
```
기대: 201 (최소금액 30,000원 "이상"이므로 5,000원 할인 적용)
실제: 400 COUPON_MIN_AMOUNT
원인: if (totalPrice <= minAmount)  ← < 여야 한다
```
→ **한 기법만으로는 못 잡는다**는 걸 보여주는 사례

### 4. 외부 공개 API에서 실제 결함 검출

자체 SUT는 내가 결함을 심었으니 검출률 100%가 실력의 증거가 못 된다.
그래서 **남이 만든 공개 API**(restful-booker)를 공식 문서·REST 규약에 대조했다.

| 결함 | 기대 → 실제 |
|---|---|
| 인증 실패 응답 | `401` → **`200 OK`** + `{"reason":"Bad credentials"}` |
| 리소스 생성 | `201` → `200` |
| 삭제 성공 | `204` → `201 "Created"` |
| 체크아웃 < 체크인 | `400` → `200` (그대로 생성됨) |
| **필수 필드 누락** | `400` → **`500 Internal Server Error`** |

마지막이 가장 심각하다. **클라이언트 실수(4xx)를 서버 장애(5xx)로 응답**하면
모니터링 알람이 오염되고, 호출자는 재시도할지 요청을 고칠지 판단할 수 없다.

## 기술적으로 신경 쓴 것

| 항목 | 내용 |
|---|---|
| **테스트 격리** | 서버 전체 초기화 대신 **테스트별 계정 생성**. 병렬 실행과 충돌하지 않는다 |
| **전역 상태 처리** | 재고는 상품별 **소유권을 명시**하고, 절대값이 아닌 **변화량**으로 검증 |
| **계약 검증** | JSON Schema에 `additionalProperties: false` + 비즈니스 제약(`stock ≥ 0`)을 넣어 결함 4건을 자동 검출 |
| **알려진 결함 관리** | `test.fail()` 로 마킹 → CI 초록불 유지 + 결함 수정 시 자동 알림 |
| **Flaky 대응** | 재시도로 덮지 않고 원인 조사. 자원 경합으로 판명 → 워커 상한(로컬 4 / CI 2) 설정 (경위를 설정 파일에 기록) |
| **명세 리뷰(정적 테스트)** | 실행 전에 기준 문서를 먼저 검증. 명세 결함 6건 별도 리포트 |
| **외부 의존 분리** | 남의 서버 장애가 우리 빌드를 막지 않도록 CI Job 분리 + `continue-on-error` |
| **리포트 자동화** | 실행 결과 JSON → QA 결과 보고서(CSV/MD) 자동 변환 |

## 알려진 한계

정직하게 밝혀 둔다.

- **자체 SUT의 결함 15건은 내가 심은 것**이다. 검출률 100%는 그 자체로 실력의 증거가 아니다.
  이를 보완한 것이 두 가지다 — 외부 공개 API에서 독립적으로 검출한 결함 5건,
  그리고 **정답지에 없던 BUG-016**(합산 시 수량 상한 미검사). 후자는 SUT를 만든 사람도
  몰랐던 명세 위반이라, 명세만 보고 설계했을 때 무엇이 나오는지를 보여주는 유일한 사례다
- **동시성 테스트가 없다.** 마지막 재고 1개를 두 사용자가 동시에 주문하는 경우는 미검증이다
- **성능 기준선이 없다.** 응답시간 상한만 확인하고 기준선 측정은 하지 않았다
- 외부 UI 테스트(SauceDemo)가 정상 경로에 치우쳐 있다. `problem_user` 시나리오 확대가 필요하다
- **CI(`.github/workflows/qa.yml`)를 실제로 가동해 본 적이 없다.** 로컬에서 설계·작성만 했고, 이 저장소에
  올린 뒤 첫 실행에서 확인해야 할 부분이다. 미리 밝히지 않고 있다가 들키는 것보다는 낫다고 판단했다
- **자동 생성 문서와 손으로 쓴 문서의 노후화 속도가 다르다.** `artifacts/04`(자동 생성)는 재실행할 때마다
  갱신되지만, `artifacts/05`·이 README처럼 손으로 쓴 문서는 그대로 남아 수치가 벌어질 수 있다.
  실제로 이번 정비(168→176건) 전까지 그 간극이 존재했다
