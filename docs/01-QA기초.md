# SW QA 기초 — 용어와 프로세스

---

## 1. QA / QC / Testing 은 다르다

면접에서 자주 묻는다. 헷갈리면 티가 난다.

| 구분 | 목적 | 시점 | 예 |
|---|---|---|---|
| **QA** (Quality Assurance) | 결함이 **생기지 않게** 프로세스를 만든다 | 전 과정 | 코드리뷰 규칙 수립, 정의된 완료 기준(DoD), 릴리스 프로세스 |
| **QC** (Quality Control) | 만들어진 산출물에서 결함을 **찾아낸다** | 산출물 완성 후 | 테스트 수행, 검수 |
| **Testing** | QC를 수행하는 구체적 활동 | 실행 시점 | 테스트케이스 작성·실행 |

한 줄 요약: **QA는 예방, QC는 검출, Testing은 그 수단.**
실무에서 "QA 엔지니어"는 셋을 다 한다.

### Verification vs Validation

| | 질문 | 방법 |
|---|---|---|
| **Verification** (검증) | "명세대로 만들었는가?" | 리뷰, 정적 분석, 테스트 |
| **Validation** (확인) | "사용자가 원하던 게 맞는가?" | 사용성 테스트, UAT, 베타 |

명세대로 완벽히 만들었는데 아무도 안 쓰는 기능일 수 있다. 그게 Validation 실패다.

## 2. 테스트의 7가지 원칙 (ISTQB)

| 원칙 | 의미 | 실무에서의 함의 |
|---|---|---|
| 1. 테스트는 결함의 **존재**를 밝힐 뿐, 부재를 증명하지 못한다 | 버그가 없음을 증명할 수는 없다 | "테스트 다 통과했으니 버그 없습니다"는 틀린 말 |
| 2. **완벽한 테스트는 불가능**하다 | 입력 조합은 무한하다 | 그래서 설계 기법으로 줄인다 |
| 3. **조기 테스트**가 비용을 줄인다 | 요구사항 단계 결함이 가장 싸다 | 명세 리뷰가 테스트 실행보다 ROI가 높다 |
| 4. 결함은 **집중**된다 (파레토) | 20% 모듈에서 80% 결함 | 결함 많이 난 곳을 더 본다 |
| 5. **살충제 역설** | 같은 테스트만 반복하면 새 결함을 못 잡는다 | 케이스를 주기적으로 갱신, 탐색적 테스트 병행 |
| 6. 테스트는 **정황에 의존**한다 | 은행 앱과 게임의 기준이 다르다 | 도메인 리스크에 맞춰 전략을 짠다 |
| 7. **오류 부재의 궤변** | 명세대로 만들어도 쓸모없으면 실패 | Validation 없이 Verification만 하면 안 된다 |

> 4번과 5번은 이 프로젝트에도 그대로 나타난다.
> 주입 결함 15건 중 6건이 "경계값 처리"에 몰려 있고(4번),
> 결정표 테스트 6건은 결함을 하나도 못 잡았다(5번의 예고편 — 이미 통과하는 영역).

## 3. 테스트 레벨

```
                 ┌──────────────────┐
                 │  인수 테스트       │  발주자/사용자가 "받아도 되는가" 판단 (UAT)
                 ├──────────────────┤
                 │  시스템 테스트     │  완성된 시스템 전체. 기능 + 비기능
                 ├──────────────────┤
                 │  통합 테스트       │  모듈 간 인터페이스. API 테스트가 주로 여기
                 ├──────────────────┤
                 │  단위 테스트       │  함수/클래스 하나. 주로 개발자가 작성
                 └──────────────────┘
```

이 프로젝트의 위치
- `tests/api/` → **통합 테스트** (HTTP 인터페이스를 통한 검증)
- `tests/ui/` → **시스템 테스트** (화면부터 DB까지 전체 경로)
- `TC-UI-E2E-001` → **인수 테스트 성격** (사용자 시나리오 전체)

## 4. 테스트 유형

| 유형 | 확인하는 것 | 이 프로젝트의 예 |
|---|---|---|
| **기능 테스트** | 무엇을 하는가 | 주문이 되는가, 할인이 맞는가 |
| **비기능 테스트** | 얼마나 잘 하는가 | 응답시간, 부하, 보안, 사용성, 호환성 |
| **구조 테스트** | 코드 구조 커버리지 | 구문/분기 커버리지 |
| **재확인 테스트** (Confirmation) | 고친 게 진짜 고쳐졌나 | 결함 수정 후 해당 TC 재실행 |
| **회귀 테스트** (Regression) | 고치면서 다른 데 안 깨졌나 | 전체 자동화 스위트 재실행 |

> **재확인 ≠ 회귀.** 재확인은 그 버그 하나, 회귀는 나머지 전부.
> 자동화의 가장 큰 가치가 바로 회귀 테스트다. 손으로는 매번 168건을 돌릴 수 없다.

## 5. 테스트 프로세스

```
계획 ─▶ 모니터링/제어 ─▶ 분석 ─▶ 설계 ─▶ 구현 ─▶ 실행 ─▶ 완료
 │                        │       │       │       │       │
 테스트계획서          테스트베이스  TC명세  테스트  결함     테스트
                       분석,      작성    데이터  리포트   요약보고서
                     테스트조건               환경준비
```

| 단계 | 하는 일 | 산출물 |
|---|---|---|
| **계획** | 범위·전략·자원·일정·종료조건 결정 | 테스트 계획서 |
| **분석** | 요구사항에서 "무엇을 테스트할지"(테스트 조건) 도출 | 테스트 조건 목록 |
| **설계** | 기법을 적용해 테스트케이스 도출 | 테스트케이스 명세 |
| **구현** | 테스트 데이터·환경·스크립트 준비 | 자동화 코드, 테스트 데이터 |
| **실행** | 수행하고 결과를 기록, 결함 리포팅 | 수행 결과, 결함 리포트 |
| **완료** | 결과 정리, 회고, 자산 보존 | 테스트 요약 보고서 |

## 6. 개발 모델과 테스트

### V-모델

```
요구사항 정의 ──────────────────────▶ 인수 테스트
   설계 ─────────────────────────▶ 시스템 테스트
      상세설계 ──────────────▶ 통합 테스트
          구현 ──────────▶ 단위 테스트
```

왼쪽 각 단계에서 **대응하는 테스트를 미리 설계**한다는 것이 핵심이다.
"개발 다 끝나고 테스트 시작"이 아니다.

### 애자일에서의 테스트

| 개념 | 의미 |
|---|---|
| **시프트 레프트** (Shift Left) | 테스트를 개발 초기로 당긴다. 요구사항 리뷰부터 QA가 참여 |
| **DoD** (Definition of Done) | "완료"의 기준에 테스트 통과를 포함시킨다 |
| **테스트 피라미드** | 단위 多 → 통합 中 → E2E 少 |
| **CI/CD** | 커밋마다 자동 테스트. 이 프로젝트의 `.github/workflows/qa.yml` |

## 7. 자주 쓰는 용어

| 용어 | 의미 |
|---|---|
| **Test Basis** | 테스트 설계의 근거가 되는 문서 (요구사항 명세, 화면설계서 등) |
| **Test Condition** | 테스트로 확인할 대상 (예: "비밀번호 길이 검증") |
| **Test Case** | 조건 + 입력 + 기대결과 (예: "7자 입력 → 400") |
| **Test Suite** | 테스트케이스의 묶음 |
| **Test Oracle** | 기대결과의 판단 근거 (명세서, 유사 시스템, 도메인 지식) |
| **Error / Defect / Failure** | 사람의 **실수**(Error) → 코드의 **결함**(Defect) → 실행 시 **장애**(Failure) |
| **Traceability** | 요구사항 ↔ 테스트케이스 ↔ 결함의 연결 관계 |
| **Coverage** | 테스트가 커버한 비율 (요구사항/코드/데이터 기준) |
| **Flaky Test** | 같은 코드인데 통과했다 실패했다 하는 불안정한 테스트 |
| **DDE** | 결함 검출 효율. 주입 결함 중 몇 %를 잡았는지 |

### Error / Defect / Failure 예시

```
개발자가 "8자 이상"만 생각하고 상한을 잊음          → Error   (사람의 실수)
     ↓
if (pw.length < 8) 만 있고 상한 검사가 없음        → Defect  (코드의 결함)
     ↓
21자 비밀번호로 가입이 되어버림                     → Failure (실행 결과)
```

결함 리포트에는 **Failure**를 쓰고, 원인 분석에 **Defect**를 쓴다.
