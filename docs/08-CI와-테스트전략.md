## 1. 테스트 피라미드

```
         ▲                          비용 ↑  속도 ↓  안정성 ↓
        ╱ ╲    E2E (4건)
       ╱   ╲   사용자 핵심 경로만
      ╱─────╲
     ╱       ╲  통합/API (91건)
    ╱         ╲ 경우의 수 대부분
   ╱───────────╲
  ╱             ╲ 단위 (개발자 영역)
 ╱───────────────╲
                            비용 ↓  속도 ↑  안정성 ↑
```

### 안티패턴: 아이스크림 콘

```
 ╲─────────────╱   E2E 잔뜩
  ╲───────────╱    통합 조금
   ╲─────────╱     단위 거의 없음
```

"화면으로 다 테스트하면 되지"의 결과다. 증상:
- 전체 실행에 2시간
- 매번 몇 개씩 랜덤 실패
- 실패해도 원인 파악에 30분
- 결국 아무도 안 본다

### 이 프로젝트의 배분

| 레벨 | 건수 | 비중 | 평균 시간 |
|---|---:|---:|---:|
| API | 91 | 67% | 0.2초 |
| UI 통합 | 16 | 12% | 3초 |
| UI E2E | 4 | 3% | 4초 |
| 외부(참고) | 24 | 18% | 3초 |

(UI 20건은 3개 브라우저에서 각각 실행되어 실제 수행은 60건. 비중은 테스트 정의 135건 기준)

**"비밀번호 8자 경계"는 API에서만 본다.** UI에서는 "실패 메시지가 뜨는가"만 확인한다.
같은 검증을 두 레벨에서 반복하면 유지보수 비용만 두 배가 된다.

## 2. 무엇을 자동화하고 무엇을 하지 않는가

### 자동화가 이기는 것
- 회귀 테스트 (매 릴리스마다 반복)
- 데이터 조합이 많은 검증 (경계값 × 4, 결정표 × 6)
- API 계약 검증
- 크로스 브라우저
- **화면으로는 만들 수 없는 입력** (음수 수량, 잘못된 타입)

### 사람이 이기는 것
- 탐색적 테스트 ("어? 이거 이상한데")
- 사용성·심미성 판단
- 새로 만든 기능의 첫 검증 (요구사항이 흔들리는 시기)
- 1회성 검증

> **"자동화율 100%"는 목표가 아니다.** 자동화는 수단이고, 목표는 결함을 싸게 찾는 것이다.
> 한 번 쓰고 버릴 테스트를 자동화하면 순손실이다.

## 3. CI 파이프라인 설계

### 이 프로젝트의 구성 (`.github/workflows/qa.yml`)

| Job | 언제 | 실패 시 |
|---|---|---|
| `local` (MiniShop API + UI) | push(main·master) · PR(대상 main·master) · 매일 정기 · 수동 | **PR 필수 체크 — 병합 차단** |
| `cross-browser` (Firefox + WebKit) | push(main·master) · 정기 · 수동 (PR에서는 건너뜀) | 실행 실패로 표시 (PR 필수 체크 아님) |
| `external` (외부 데모) | 모든 실행 | **차단 안 함** (`continue-on-error`) |
| `newman` (Postman) | 모든 실행 | **PR 필수 체크 — 병합 차단**. 알려진 결함(BUG-001/006/008)의 예상 재현은 별도 판정 |

### 왜 나누는가

**외부 서비스 테스트를 메인 Job에 섞으면 안 된다.**
남의 서버가 죽었다고 우리 PR이 머지 안 되는 건 말이 안 된다.
그렇다고 안 돌리면 언제 깨졌는지 모른다. → **분리하고 실패를 허용하되 기록은 남긴다.**

### 실행 시간 관리

| 단계 | 목표 시간 | 범위 |
|---|---|---|
| PR 체크 | 5분 이내 | API + UI(Chromium) + Newman(필수 체크) |
| main 머지 | 15분 이내 | + 크로스 브라우저 |
| 야간 정기 | 제한 없음 | 전체 + 외부 |

외부 테스트는 PR에서도 참고용으로 실행하며(실패해도 차단 안 함), push(main·master)·정기·수동 실행에는 크로스 브라우저도 포함한다.

PR 체크가 10분을 넘으면 개발자가 CI를 안 기다리기 시작한다. **속도가 곧 채택률**이다.

## 4. 테스트 신뢰도 관리

### 깨진 창문 이론

빨간불이 3일 이상 방치되면 팀 전체가 실패에 무뎌진다.
그때부터 CI는 아무 의미가 없다.

**원칙: 메인 스위트는 항상 초록불이어야 한다.**

미수정 결함이 있는 상태에서 초록불을 유지하는 방법:

```ts
test('TC-API-ORDER-001 | [경계값] 주문금액이 최소주문금액과 정확히 같으면 쿠폰이 적용된다', async ({ shop }) => {
  test.fail(true, 'BUG-011: 최소주문금액 비교를 초과(>)로 하여 정확히 같은 금액이 거부된다');
  ...
});
```

| 방식 | 결함 문서화 | 수정 시 알림 | 평가 |
|---|---|---|---|
| 테스트를 안 씀 | ❌ | ❌ | 최악 |
| `test.skip()` | △ | ❌ | 영원히 잊힌다 |
| 실패한 채로 방치 | ○ | ❌ | 팀이 무뎌진다 |
| **`test.fail()`** | ○ | **○** | **권장** |

### Flaky 테스트 대응 정책

1. **재시도로 덮지 않는다.** `retries: 3` 은 문제를 숨기는 것이다
   (이 프로젝트: 로컬 0회, CI 1회, 외부 서비스만 2회)
2. Flaky가 발견되면 **원인을 찾을 때까지 격리**한다
3. 자주 나오는 원인: 명시적 sleep, 테스트 간 데이터 공유, 절대값 단언, 자원 경합

## 5. 실제 사례 — Flaky 조사 기록

### 증상
전체 프로젝트(`npx playwright test`)를 돌리면 Firefox 6건이 40~60초 타임아웃으로 실패.
개별 프로젝트로 돌리면 전부 통과.

### 조사
| 가설 | 검증 | 결과 |
|---|---|---|
| Firefox 호환성 문제 | `--project=ui-firefox` 단독 실행 | **19건 전부 통과** → 기각 |
| 테스트 간 데이터 간섭 | 계정은 이미 테스트별 생성 | 당시 기각. 다만 계정 분리만으로 공유 재고 간섭까지 배제할 수는 없다 |
| 자원 경합 | 워커 2개로 제한 후 실행 | **전부 통과** → 가장 유력(추정) |

### 원인 (추정)
기본 워커 수(코어수/2 = 9)로 6개 프로젝트를 동시 실행 →
여러 브라우저 인스턴스와 단일 스레드 SUT가 같은 PC에서 동시에 동작.
브라우저 기동에 시간이 걸려 타임아웃에 걸린 것으로 보인다.

### 조치
`workers: process.env.CI ? 2 : 4` 로 상한 설정. 경위를 설정 파일 주석으로 남김.
실험은 2개로 했고, CI는 그 값을 그대로 쓴다. 로컬은 자원이 더 여유로워 4로 뒀다
(로컬에서 4로 전체 실행해도 Fail 0 을 확인했다).

### 결과
조치 당시 전체 168건 **Fail 0** (Pass 127 / 알려진 결함 재현 41). 현재 스위트는 176건이다(2026-09-09 실행: 정상 Pass 139 / 알려진 실패 재현 37).

> **교훈: "가끔 실패한다"의 원인이 항상 테스트 코드인 것은 아니다.**
> 실행 환경도 함께 의심해야 하고, 조사 과정을 기록으로 남겨야 다음 사람이 반복하지 않는다.

## 6. 리포팅

### 개발팀용
- Playwright HTML 리포트 (trace/screenshot/video 포함)
- CI 아티팩트로 업로드, 30일 보존

### 관리자/QA 산출물용
- `node utils/report-to-csv.js` 로 실행 결과 JSON → CSV + 요약 MD 자동 변환
- TC ID / 판정 / 관련 결함 / 소요시간이 표로 정리됨

**리포트는 자동 생성해야 한다.** 손으로 옮기면
① 시간이 오래 걸리고 ② 틀리고 ③ 결국 안 하게 된다.

## 7. 릴리스 판단 기준

종료 조건(Exit Criteria)은 **테스트 시작 전에** 합의해야 한다.
끝나고 정하면 "이 정도면 됐지"가 되어버린다.

| 조건 | 기준 |
|---|---|
| 계획 TC 수행률 | 100% |
| Critical / Major 잔존 | 0건 |
| Minor 잔존 | 릴리스 노트 명시 후 허용 |
| 자동화 스위트 | 미수정 결함 제외 전부 통과 |
| 회귀 테스트 | 결함 수정 후 전체 재실행 통과 |

### 현재 상태 (MiniShop v1.0, 2026-09-09 전체 실행 기준)

| 조건 | 결과 | 판정 |
|---|---|---|
| TC 수행률 | 152/152 (MiniShop: API 91 + UI 20×3 + 초기화 1, 100%) | ✅ |
| Critical 잔존 | **4건** (BUG-013은 2026-09-07 수정·재확인) | ❌ |
| Major 잔존 | **6건** | ❌ |

→ **릴리스 불가.** 잔존 Critical 4건은 데이터 무결성(재고 음수)과 보안(XSS 위험, 계정 잠금 무력화, 로그아웃 무효)에
직결되므로 수정 후 재확인이 필요하다.
