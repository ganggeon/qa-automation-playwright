# 테스트 설계 기법 정리

> 테스트케이스를 "생각나는 대로" 만들면 세 가지 문제가 생긴다.
> ① 빠뜨린다 ② 같은 걸 여러 번 한다 ③ 왜 그 케이스를 만들었는지 설명하지 못한다.
> 설계 기법은 이 셋을 동시에 해결한다.
>
> 실제 적용 결과: [artifacts/02-테스트케이스-명세.md](../artifacts/02-테스트케이스-명세.md)

## 큰 그림

```
                    테스트 설계 기법
                          │
        ┌─────────────────┼─────────────────┐
        │                 │                 │
   명세 기반          구조 기반          경험 기반
  (블랙박스)        (화이트박스)      (Experience-based)
        │                 │                 │
  · 동등분할         · 구문 커버리지     · 오류 추정
  · 경계값 분석      · 분기 커버리지     · 탐색적 테스트
  · 결정표           · 조건 커버리지     · 체크리스트
  · 상태 전이        · 경로 커버리지
  · 유스케이스
  · 페어와이즈
```

QA가 주력으로 쓰는 건 **명세 기반**이다. 구조 기반은 주로 개발자가 단위 테스트에서 쓴다.
경험 기반은 명세 기반으로 뼈대를 만든 **뒤에** 얹는다. 순서가 바뀌면 커버리지에 구멍이 생긴다.

## 1. 동등분할 (Equivalence Partitioning)

### 개념
입력값 전체를 "같은 방식으로 처리될 그룹"으로 나누고, 각 그룹에서 **대표값 1개씩만** 테스트한다.

### 왜 유효한가
비밀번호 8자가 통과하면 9자, 10자, 11자도 같은 `if` 문을 탄다. 같은 코드 경로를
반복해서 밟는 건 시간 낭비다. **1개면 그룹 전체를 대표한다**고 보는 것이 이 기법의 전제다.

### 절차
1. 입력 조건을 하나 고른다
2. 유효 클래스(Valid)와 무효 클래스(Invalid)로 나눈다
3. **무효 클래스는 잘게 나눈다** — 각각 다른 코드 경로일 가능성이 높다
4. 클래스마다 대표값 1개를 뽑는다

### 예: 나이 입력 (14~120)

| 클래스 | 종류 | 대표값 |
|---|---|---|
| 14 미만 | 무효 | 10 |
| 14 ~ 120 | 유효 | 30 |
| 120 초과 | 무효 | 150 |
| 정수가 아님 | 무효 | 25.5 |
| 숫자가 아님 | 무효 | `"서른"` |
| 없음 | 무효 | (필드 생략) |

> **주의**: 유효 클래스는 여러 개를 한 번에 묶어 테스트해도 되지만,
> **무효 클래스는 반드시 하나씩 따로** 테스트한다. 두 개를 같이 넣으면
> 어느 쪽 때문에 실패했는지 알 수 없다(오류 마스킹).

## 2. 경계값 분석 (Boundary Value Analysis, BVA)

### 개념
동등분할의 짝꿍. 클래스의 **가장자리** 값을 테스트한다.

### 왜 유효한가
결함은 구간 한가운데가 아니라 경계에 몰린다. 이유는 단순하다 —
`<` 와 `<=`, `>` 와 `>=` 를 헷갈리고, 배열 인덱스에서 1을 더하거나 빼는 실수를 하기 때문이다.

### 절차 (2-value 방식)
유효 구간이 `min ~ max` 라면 → **min-1, min, max, max+1** 4개를 테스트한다.

```
        min-1      min                     max      max+1
   ───────┼─────────┼───────────────────────┼─────────┼───────
        무효    │◄──────── 유 효 ─────────►│      무효
```

### 3-value 방식
더 엄격하게 하려면 `min-1, min, min+1, max-1, max, max+1` 6개를 본다.
안전이 중요한 시스템(의료·금융·항공)에서 쓴다. 일반 웹 서비스는 2-value로 충분하다.

### 놓치기 쉬운 경계

| 유형 | 예 |
|---|---|
| 컬렉션 크기 | 0건 / 1건 / 최대건수 / 최대+1건 |
| 문자열 길이 | 빈 문자열 / 1자 / 최대 / 최대+1 |
| 날짜 | 어제 / 오늘 / 내일, 월말·연말, 윤년 2/29 |
| 숫자 | 0, -1, 최대 정수, 소수점 |
| 페이지네이션 | 첫 페이지 / 마지막 페이지 / 마지막+1 |
| 금액 | 0원, 할인 = 총액, 할인 > 총액 |

> 이 프로젝트에서 경계값 분석으로 분류된 검출 결함은 6건이다(MiniShop 16건 중 37.5%).
> 아래는 검출 기법이 아니라 결함의 성격(경계 계열)으로 다시 센 6건이다. 두 분류는 BUG-013·016에서 다르다.
>
> **방향은 한쪽으로 쏠려 있지 않았다.** 상한 검증 누락 2건, 하한 검증 누락·오류 3건,
> 비교 방향 오류(`≥`를 `>`로) 1건이다. "개발자는 상한을 빼먹는다"는 흔한 통념과 달리
> 실제로는 **어느 쪽이든 한쪽 끝이 비는 것**이 패턴이었다(6건 중 5건).
>
> 그래서 결론은 "상한을 조심하라"가 아니다. **min·max 어느 한쪽만 확인하는 것은 의미가 없고,
> 네 점(min-1, min, max, max+1)을 기계적으로 다 찍어야 한다.**
> 어느 쪽이 빌지는 미리 알 수 없기 때문이다.

## 3. 결정표 테스트 (Decision Table Testing)

### 개념
여러 조건이 조합되어 결과가 갈릴 때, 조건-결과 매트릭스를 만들어 규칙별로 테스트한다.

### 언제 쓰나
- 할인/요금 정책
- 권한 판정 (역할 × 리소스 × 액션)
- 승인 워크플로
- "A이면서 B가 아니고 C인 경우" 같은 복합 조건이 명세에 나올 때

### 절차
1. 조건(Condition)과 결과(Action)를 나열한다
2. 모든 조합을 적는다 (조건 n개 → 2ⁿ 열)
3. **무관(`-`)을 표시해 열을 병합한다** ← 이게 핵심이다
4. 남은 규칙마다 테스트케이스 1개

### 예: 배송비 정책

> "회원은 3만원 이상 무료배송, 비회원은 5만원 이상 무료배송. 도서산간은 항상 3,000원 추가."

| 조건 | R1 | R2 | R3 | R4 | R5 | R6 |
|---|:-:|:-:|:-:|:-:|:-:|:-:|
| 회원인가 | Y | Y | N | N | - | - |
| 주문금액 ≥ 3만 | N | Y | - | - | - | - |
| 주문금액 ≥ 5만 | - | - | N | Y | - | - |
| 도서산간인가 | N | N | N | N | Y | Y |
| **배송비** | 3,000 | 0 | 3,000 | 0 | +3,000 | +3,000 |

### 함정
결정표는 **조건의 Y/N만 본다.** "주문금액 ≥ 3만" 이 Y인지 N인지는 확인하지만,
**정확히 3만원일 때 Y인가 N인가**는 확인하지 않는다.
→ 반드시 **경계값 분석과 함께** 써야 한다. 이 프로젝트의 BUG-011이 정확히 그 지점에서 나왔다.

## 4. 상태 전이 테스트 (State Transition Testing)

### 개념
시스템이 상태를 갖고, **같은 입력이라도 현재 상태에 따라 결과가 다를 때** 쓴다.

### 언제 쓰나
- 로그인 실패 누적 → 계정 잠금
- 주문 상태: 접수 → 결제완료 → 배송중 → 배송완료 / 취소
- 세션·토큰 생명주기
- 결제 승인/취소/부분취소
- 문서 작성중 → 상신 → 승인/반려

### 절차
1. 상태를 모두 나열한다
2. 상태 전이도를 그린다
3. 각 전이(화살표)마다 테스트케이스 1개 → **0-스위치 커버리지**
4. 연속된 두 전이 조합까지 → **1-스위치 커버리지**
5. **불법 전이**도 테스트한다 ← 여기서 결함이 많이 나온다

### 예: 주문 상태

```
 [접수] ──결제──▶ [결제완료] ──출고──▶ [배송중] ──수령──▶ [배송완료]
   │                  │                                        │
  취소               취소                                     반품
   ▼                  ▼                                        ▼
 [취소]             [취소]                                   [반품]
```

**불법 전이 테스트 (중요)**
- 배송중 상태에서 취소 요청 → 거부되어야 한다
- 배송완료 상태에서 다시 출고 → 거부되어야 한다
- 취소된 주문을 다시 결제 → 거부되어야 한다

> 개발자는 정상 흐름을 먼저 만들고 "이상한 순서"는 나중에 처리한다.
> 그 "나중"이 안 오는 경우가 많다. **불법 전이는 결함 밀집 구역이다.**

## 5. 페어와이즈 / 조합 테스트 (Pairwise Testing)

### 개념
파라미터가 많아 전수 조합이 불가능할 때, **모든 값 쌍(pair)이 최소 1번씩** 등장하도록 조합을 줄인다.

### 근거
경험적으로 결함의 대부분은 **1개 또는 2개 파라미터의 상호작용**에서 발생한다.
3개 이상이 동시에 맞물려야 나오는 결함은 드물다.

### 예

| 파라미터 | 값 |
|---|---|
| 브라우저 | Chrome, Firefox, Safari |
| OS | Windows, macOS |
| 회원등급 | 일반, VIP |
| 결제수단 | 카드, 계좌이체, 간편결제 |

- 전수 조합: 3 × 2 × 2 × 3 = **36가지**
- 페어와이즈: **약 9가지** (모든 두 값의 쌍은 전부 포함됨)

### 도구
손으로 만들지 않는다. `PICT`(Microsoft), `AllPairs`, `pict-node` 같은 도구를 쓴다.

## 6. 오류 추정 / 탐색적 테스트 (Experience-based)

### 개념
경험과 직관으로 "여기가 수상하다"를 찍는다. 기법이 아니라 **감각**이다.

### 언제 쓰나
- 정형 기법으로 케이스를 다 만든 **뒤**
- 명세가 없거나 부실할 때
- 시간이 없어 리스크 높은 곳부터 봐야 할 때

### 자주 통하는 체크리스트

| 영역 | 의심할 것 |
|---|---|
| 숫자 | 0, 음수, 소수점, 아주 큰 값, 천 단위 구분자 포함 문자열 |
| 문자열 | 빈 값, 공백만, 이모지, 한글/중국어, HTML 태그, SQL 예약어, 아주 긴 문자열 |
| 날짜 | 2/29, 12/31, 서머타임, 타임존, 미래·과거 극단값 |
| 동시성 | 같은 상품을 동시에 마지막 1개 주문, 이중 클릭, 새로고침 연타 |
| 순서 | 뒤로가기 후 재제출, 결제 후 새로고침, 로그아웃 후 뒤로가기 |
| 권한 | 남의 ID로 조회/수정/삭제, 로그아웃 후 API 직접 호출 |
| 금액 | 할인 > 원금, 무료배송 경계, 부분 취소 후 잔액 |

> 이 프로젝트에서 오류 추정으로만 결함 5건을 잡았다.
> "돈 계산에는 하한 처리가 빠진다", "삭제 API는 존재 확인을 빼먹는다" 같은
> **패턴화된 직관**이 실제로 통한다.

## 7. 기법 선택 가이드

| 상황 | 쓸 기법 |
|---|---|
| 입력 필드 하나에 규칙이 있다 | 동등분할 + 경계값 |
| 조건 여러 개가 얽혀 결과가 갈린다 | 결정표 |
| 순서·이력에 따라 결과가 달라진다 | 상태 전이 |
| 설정 조합이 폭발한다 | 페어와이즈 |
| 사용자 시나리오 전체를 훑고 싶다 | 유스케이스 테스트 (E2E) |
| 명세가 없다 / 시간이 없다 | 탐색적 테스트 |

**실무에서는 섞어 쓴다.** 이 프로젝트의 주문 기능만 봐도:
- 결정표로 규칙 6개(성공 2 · 거부 4) → 명세대로 동작함을 확인
- 경계값으로 최소주문금액 경계 → BUG-011
- 오류 추정으로 음수 결제금액 → BUG-013

한 기법만으로는 못 잡았을 결함들이다.
