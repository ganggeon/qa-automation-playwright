# SW QA 학습 로드맵

> 이 프로젝트를 따라가며 QA 실무 역량을 쌓는 8주 계획.
> 각 주차는 **읽기 → 직접 해보기 → 산출물 남기기** 순으로 구성했다.
> 산출물이 곧 포트폴리오가 된다.

---

## 전체 그림

```
1~2주  QA 기초 + 테스트 설계 기법        → 문서 QA 역량
3~4주  API 테스트 (Postman → 코드)       → 자동화 진입
5~6주  UI 자동화 (Playwright + POM)      → E2E 역량
7주    CI/CD + 리포팅                    → 팀 프로세스 이해
8주    정리 + 면접 대비                   → 포트폴리오 완성
```

---

## 1주차 — QA 기초

**읽기**: [01-QA기초.md](01-QA기초.md)

**핵심 개념**
- QA / QC / Testing의 차이
- 테스트 7원칙 (특히 "결함 집중", "살충제 역설")
- 테스트 레벨(단위·통합·시스템·인수)과 유형
- Error / Defect / Failure 구분

**해보기**
1. `sut/SPEC.md` 를 읽고 **테스트 조건 목록**을 만든다 (아직 테스트케이스가 아니다)
   - 예: "비밀번호 길이 검증", "쿠폰 최소주문금액 판정", "계정 잠금"
2. 각 조건에 리스크 등급을 매긴다 (금전·보안 관련이 상위)

**산출물**: 테스트 조건 목록 + 리스크 순위

> **팁**: 이 단계에서 명세의 모호한 부분을 찾아 질문 목록을 만들어라.
> "만료일 당일 자정 기준인가?" 같은 질문을 던지는 것이 실무 QA의 첫 번째 기여다.

## 2주차 — 테스트 설계 기법

**읽기**: [02-테스트설계기법.md](02-테스트설계기법.md), [03-테스트케이스-작성법.md](03-테스트케이스-작성법.md)

**핵심 개념**
- 동등분할 / 경계값 분석 (이 둘이 전체의 절반)
- 결정표 / 상태 전이
- 페어와이즈 / 오류 추정

**해보기**
1. FR-01(회원가입)에 동등분할 + 경계값을 적용해 테스트케이스를 표로 작성
2. FR-09(주문)의 결정표를 직접 그린다 — 조건 5개 → 몇 개 규칙으로 줄어드는가
3. FR-02(로그인)의 상태 전이도를 그리고 전이마다 케이스를 만든다
4. **작성 후** [artifacts/02-테스트케이스-명세.md](../artifacts/02-테스트케이스-명세.md) 와 비교한다

**산출물**: 기법별 테스트케이스 표 (Excel 또는 Markdown)

> **이 주차가 가장 중요하다.** 자동화는 도구를 배우면 되지만,
> "무엇을 테스트할지 정하는 능력"은 대체가 안 된다.
> 면접에서도 여기를 가장 깊게 파고든다.

## 3주차 — API 테스트 기초 (Postman)

**읽기**: [05-API테스트.md](05-API테스트.md)

**핵심 개념**
- HTTP 메서드, 상태 코드 (특히 401 vs 403, 400 vs 500)
- 요청/응답 구조, 헤더, 인증
- 멱등성

**해보기**
1. `npm run sut` 으로 SUT를 띄운다
2. Postman으로 직접 요청을 보내본다 (회원가입 → 로그인 → 담기 → 주문)
3. 2주차에 만든 케이스 중 API로 검증 가능한 것을 컬렉션으로 만든다
4. `pm.test()` 로 단언을 추가한다
5. `npm run newman` 으로 CLI 실행

**산출물**: Postman 컬렉션 + Newman HTML 리포트

## 4주차 — API 테스트 자동화 (코드)

**읽기**: [06-Playwright-기초.md](06-Playwright-기초.md) 1~2장, [07-TypeScript-for-JS개발자.md](07-TypeScript-for-JS개발자.md) 1장

**핵심 개념**
- Playwright `request` 픽스처
- 테스트 격리(각 테스트가 자기 데이터를 준비)
- JSON 스키마 검증

**해보기**
1. `tests/api/01-signup.spec.ts` 를 읽고 구조를 파악한다
2. **직접 TC를 1건 추가한다** — 예: "나이에 문자열을 넣으면 400"
3. `test-data/schemas.ts` 에 스키마를 하나 추가하고 `expectSchema()` 로 검증
4. 데이터 주도 테스트(`for` 루프 + 케이스 배열)를 직접 작성

**산출물**: 추가한 테스트케이스 (PR 형태로 커밋)

> **TypeScript는 여기서 처음 만난다.** 1장만 읽고 시작해도 충분하다.
> 막히면 `: string` 같은 타입 표기를 지우고 돌려봐라 — 거의 다 동작한다.

## 5주차 — UI 자동화 기초

**읽기**: [06-Playwright-기초.md](06-Playwright-기초.md) 전체

**핵심 개념**
- 로케이터 우선순위 (`getByRole` > `getByTestId` > CSS)
- 자동 대기 — `waitForTimeout` 을 쓰지 않는 법
- `expect(locator)` vs `expect(value)`

**해보기**
1. `npx playwright codegen http://localhost:4010` 으로 조작을 녹화해본다
2. 녹화된 코드를 **직접 다듬는다** (셀렉터를 `getByTestId` 로 교체)
3. `npm run test:headed` 로 브라우저를 보면서 실행
4. 일부러 셀렉터를 틀리게 만들고 `--debug` / Trace Viewer로 디버깅해본다

**산출물**: UI 테스트 1건 + trace 파일

## 6주차 — Page Object Model + E2E

**읽기**: [06-Playwright-기초.md](06-Playwright-기초.md) 3장, [07-TypeScript-for-JS개발자.md](07-TypeScript-for-JS개발자.md) 전체

**핵심 개념**
- POM 원칙: 페이지 객체는 검증하지 않는다
- 픽스처 확장
- 테스트 데이터 소유권

**해보기**
1. `pages/` 의 페이지 객체를 읽고 구조를 파악
2. **주문내역 화면의 페이지 객체(`OrdersPage`)를 직접 만든다**
3. 그것을 쓰는 E2E 테스트를 1건 작성
4. `npm run test:crossbrowser` 로 3개 브라우저에서 돌려본다

**산출물**: 새 페이지 객체 + E2E 테스트

## 7주차 — CI/CD와 리포팅

**읽기**: [08-CI와-테스트전략.md](08-CI와-테스트전략.md)

**핵심 개념**
- 테스트 피라미드
- Flaky 테스트 대응
- `test.fail()` 로 알려진 결함 관리
- 종료 조건(Exit Criteria)

**해보기**
1. GitHub에 저장소를 만들고 push → Actions가 도는 것을 확인
2. `node utils/report-to-csv.js` 실행 → CSV가 만들어지는 과정을 코드로 확인
3. 일부러 SUT의 결함 하나를 **고쳐본다** (`[SEED-xx]` 주석 참고)
   → `Expected to fail, but passed` 가 뜨는 것을 확인하고 `test.fail()` 을 지운다

**산출물**: 초록불 CI 배지 + 결함 수정 → 재확인 → Closed 기록

## 학습 원칙 3가지

### 1. 코드를 읽기 전에 명세를 읽어라
`sut/server.js` 를 먼저 보면 테스트가 "구현대로" 만들어진다.
그러면 구현이 틀린 경우를 놓치기 쉽다. **명세가 기준**이다.

### 2. 기법을 먼저, 직관은 나중에
"이것도 해볼까?"로 시작하면 커버리지에 구멍이 생긴다.
동등분할·경계값으로 뼈대를 세운 뒤 오류 추정을 얹는다.

### 3. 산출물을 남겨라
공부한 내용은 잊는다. 남은 문서와 코드가 실력의 증거다.
매주 커밋하면 그 자체가 학습 이력이 된다.
