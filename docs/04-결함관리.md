# 결함 관리

---

## 1. 좋은 결함 리포트의 조건

개발자가 리포트를 받고 **되묻지 않아도 되는 것**이 좋은 리포트다.
되묻는 순간 왕복 하루가 날아간다.

| 항목 | 필수 | 설명 |
|---|---|---|
| 제목 | ● | "무엇이 어떻게 잘못됐는가"를 한 줄로 |
| 심각도 / 우선순위 | ● | 판단 근거도 함께 |
| 환경 | ● | 버전, 브라우저, OS, 계정 |
| 재현 절차 | ● | 번호를 매겨 그대로 따라할 수 있게 |
| 기대 결과 | ● | 근거가 되는 요구사항 번호와 함께 |
| 실제 결과 | ● | 응답 원문, 스크린샷, 로그 |
| 재현율 | ○ | 100% / 3회 중 1회 |
| 증거 | ○ | 스크린샷, trace, 네트워크 로그 |
| 원인 추정 | ○ | 알면 적는다. 모르면 안 적는 게 낫다 |
| 영향 범위 | ○ | 누가, 얼마나 곤란해지는가 |

### 제목 쓰기

| 나쁨 | 좋음 |
|---|---|
| 주문 오류 | 할인액이 주문금액보다 크면 결제금액이 음수(-47,655원)로 계산된다 |
| 로그인 안 됨 | 5회 로그인 실패 후에도 계정이 잠기지 않는다 (FR-02-3 위반) |
| 재고 이상함 | 재고 확인 없이 차감하여 재고가 음수(-6)가 된다 |

제목만 읽고도 **심각도를 가늠할 수 있어야** 한다.

### 재현 절차 쓰기

```
❌ 로그인해서 주문해보면 금액이 이상함

✅ 1. qa@test.com / Qa123456 으로 로그인한다
   2. 상품 '북마크 세트'(2,345원)를 1개 장바구니에 담는다
   3. 장바구니에서 쿠폰 코드 'BIG50000' 을 입력하고 [주문하기]를 누른다
   4. 응답의 finalPrice 값을 확인한다

   기대: 0 (FR-09-5 — 결제금액은 0원 미만이 될 수 없다)
   실제: -47655
```

**구체적인 값**을 적는다. "상품을 담는다"가 아니라 "북마크 세트를 1개".
값이 달라지면 재현이 안 될 수 있다.

## 2. 심각도(Severity) vs 우선순위(Priority)

**둘은 다르다.** 자주 나오는 면접 질문이다.

| | 심각도 | 우선순위 |
|---|---|---|
| 판단 주체 | QA (기술적 영향) | PO/PM (비즈니스 판단) |
| 기준 | 시스템에 미치는 영향 | 언제 고칠 것인가 |
| 예 | 데이터 손상 = Critical | 다음 주 시연 = P1 |

### 4가지 조합

| 조합 | 예 |
|---|---|
| **높은 심각도 + 높은 우선순위** | 결제금액이 음수로 계산됨 → 즉시 수정 |
| **높은 심각도 + 낮은 우선순위** | 관리자 전용 화면에서만 발생하는 데이터 손상. 사용자 1명, 우회 가능 |
| **낮은 심각도 + 높은 우선순위** | 메인 화면 회사 로고 오탈자. 내일 대외 발표 |
| **낮은 심각도 + 낮은 우선순위** | 잘 안 쓰는 설정 화면의 정렬 어긋남 |

### 심각도 기준 (이 프로젝트)

| 등급 | 정의 | 예 |
|---|---|---|
| Critical | 데이터 손상 / 금전 손실 / 보안 침해 / 우회 불가 | 음수 결제금액, 재고 음수, 계정 잠금 무력화, XSS |
| Major | 주요 기능이 명세대로 동작 안 함, 우회 어려움 | 품절 상품 주문 가능, 쿠폰 미적용 |
| Minor | 동작은 하나 명세와 다름, 우회 가능 | 검색 대소문자 구분, 응답 코드 불일치 |
| Trivial | 사용에 지장 없음 | 오탈자, 정렬 미세 어긋남 |

## 3. 결함 생명주기

```
     ┌─────────────────────────────────────────────┐
     │                                             │
  [New] ──▶ [Assigned] ──▶ [Fixed] ──▶ [Verified] ──▶ [Closed]
     │           │                          │
     │           │                       재현됨
     ▼           ▼                          ▼
 [Rejected]  [Deferred]                [Reopened]
 (결함 아님)  (차기 반영)                     │
                                            └──▶ [Assigned]
```

| 상태 | 의미 | 누가 |
|---|---|---|
| New | 등록됨 | QA |
| Assigned | 담당자 배정 | 개발 리드 |
| Fixed | 수정 완료(주장) | 개발자 |
| **Verified** | **QA가 재확인해 수정 확인** | QA |
| Closed | 종료 | QA |
| Reopened | 재확인 결과 여전히 재현됨 | QA |
| Rejected | 결함이 아님(명세대로 동작) | 개발자 + QA 합의 |
| Deferred | 인정하나 이번 릴리스에선 미수정 | PO |

> **Fixed ≠ Closed.** 개발자가 "고쳤어요"라고 한 것과 실제로 고쳐진 것은 다르다.
> QA의 재확인(Verified)을 거쳐야 Closed다. 이 원칙이 무너지면 결함 관리가 형해화된다.

### Rejected를 받았을 때

감정적으로 대응할 일이 아니다. 셋 중 하나다.
1. **명세를 내가 잘못 읽었다** → 인정하고 닫는다
2. **명세 자체가 모호하다** → 명세를 고치자고 제안한다 (이게 진짜 QA의 기여다)
3. **개발자가 명세를 잘못 읽었다** → 요구사항 번호를 인용해 근거를 댄다

## 4. 결함 지표

| 지표 | 계산 | 무엇을 알려주나 |
|---|---|---|
| **결함 밀도** | 결함 수 / 규모(KLOC, 기능점수) | 어느 모듈이 위험한가 |
| **DDE** (결함 검출 효율) | 검출 결함 / 전체 결함 × 100 | 우리 테스트가 얼마나 촘촘한가 |
| **DRE** (결함 제거 효율) | 출시 전 검출 / (출시 전 + 출시 후) × 100 | QA 프로세스 전체의 성적표 |
| **재오픈율** | Reopened / Fixed × 100 | 수정 품질 |
| **평균 수정 시간** | Fixed 시각 - Assigned 시각 | 개발 대응 속도 |
| **결함 유입 단계** | 요구사항/설계/구현 중 어디서 | 프로세스 개선 포인트 |

### 결함 주입(Defect Seeding)으로 DDE 추정하기

알려진 결함 N개를 몰래 심어두고 테스트한다.
- 주입 결함 15개 중 12개 검출 → 검출률 80%
- 실제 결함 40개 검출 → 전체 결함 추정치 = 40 / 0.8 = **50개**
- → 아직 약 10개가 남아 있다고 추정

> 이 프로젝트는 SUT에 15건을 주입하고 **15건 전부 검출**했다 (DDE 100%).
> 다만 SUT와 테스트 스위트 대부분은 Claude가 같은 학습 환경에서 구성했으므로, 이 수치를 학습자의 독립적인 검출 역량으로 볼 수는 없다.
> 그래서 외부 공개 API(restful-booker)에서 검출한 5건(관례 위반·개선 제안 4 · 명확한 결함 1)을 함께 제시한다.

## 5. 결함 리포트 템플릿

```markdown
## [BUG-0XX] 제목 — 무엇이 어떻게 잘못되는가

| 항목 | 내용 |
|---|---|
| 심각도 / 우선순위 | Critical / P1 |
| 위반 요구사항 | FR-09-5 |
| 기능 영역 | 주문/금액 |
| 발견 TC | TC-API-ORDER-003 |
| 환경 | MiniShop v1.0 / Chromium 151 / Windows 11 |
| 재현율 | 100% (5/5) |
| 상태 | New |

### 재현 절차
1. ...
2. ...

### 기대 결과
(요구사항 인용)

### 실제 결과
(응답 원문 / 스크린샷)

### 원인 분석
(코드 위치와 추정 원인 — 확실할 때만)

### 영향
(누가, 얼마나 곤란해지는가)

### 제안 수정
(코드 스니펫 — 있으면 좋지만 강요는 아니다)

### 첨부
- trace.zip
- screenshot.png
```

## 6. 개발자와 일하는 법

| 하지 말 것 | 대신 |
|---|---|
| "이거 버그예요" (근거 없이) | "FR-09-5에 따르면 0원 이상이어야 하는데 -47,655가 나옵니다" |
| 여러 결함을 한 티켓에 | 하나씩 분리 (수정·검증 단위가 다르다) |
| 재현 안 되는 걸 그냥 등록 | 재현 조건을 좁힌 뒤 등록. 못 좁히면 "재현율 3/10" 명시 |
| 수정 방법을 지시 | 영향과 근거를 전달. 방법은 개발자 몫 |
| Fixed를 그대로 신뢰 | 반드시 재확인 후 Closed |

> 결함 리포트는 **비난이 아니라 정보 전달**이다.
> "당신이 틀렸다"가 아니라 "명세와 구현이 어긋난 지점이 여기입니다"로 쓴다.
> 이 톤 하나가 협업 품질을 크게 바꾼다.
