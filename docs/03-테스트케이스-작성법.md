# 테스트케이스 작성법

---

## 1. 좋은 테스트케이스의 조건

| 조건 | 설명 |
|---|---|
| **재현 가능** | 누가 실행해도 같은 결과가 나온다 |
| **독립적** | 다른 케이스의 실행 여부·순서에 영향받지 않는다 |
| **단일 목적** | 한 케이스에서 한 가지만 검증한다 |
| **명확한 기대결과** | "정상 동작한다" ❌ / "HTTP 400과 code=INVALID_QTY를 반환한다" ✅ |
| **추적 가능** | 어떤 요구사항에서 나왔는지 알 수 있다 |
| **도출 근거가 있다** | "왜 이 값인가"에 답할 수 있다 (경계값, 동등분할 대표값 등) |

### 나쁜 예 → 좋은 예

| 나쁜 예 | 문제 | 좋은 예 |
|---|---|---|
| "로그인을 테스트한다" | 무엇을 어떻게? 기대결과는? | "잠긴 계정으로 올바른 비밀번호를 입력하면 423 ACCOUNT_LOCKED를 반환한다" |
| "수량을 여러 개 입력해본다" | 재현 불가 | "수량 0 / 1 / 99 / 100 을 각각 입력한다 (경계값)" |
| "정상적으로 처리된다" | 판정 불가 | "재고가 정확히 2 감소하고 장바구니가 비워진다" |
| "장바구니 테스트 후 주문 테스트" | 순서 의존 | 각 케이스가 자기 데이터를 스스로 준비한다 |

## 2. 테스트케이스 구성 요소

| 항목 | 설명 | 예 |
|---|---|---|
| TC ID | 고유 식별자 | `TC-API-ORDER-001` |
| 대분류/중분류 | 기능 계층 | 주문 / 쿠폰 적용 |
| 관련 요구사항 | 추적성 | FR-09-3 |
| 적용 기법 | 도출 근거 | 경계값 분석 |
| 사전조건 | 실행 전 상태 | 로그인 상태, 장바구니에 30,000원 담김 |
| 실행 절차 | 재현 단계 | 1. 쿠폰 `SAVE5000` 입력 2. 주문하기 클릭 |
| 입력 데이터 | 구체적 값 | `{ couponCode: "SAVE5000" }` |
| **기대 결과** | 판정 기준 | 201 / discount=5000 / finalPrice=25000 |
| 실제 결과 | 수행 후 기록 | 400 COUPON_MIN_AMOUNT |
| 판정 | Pass/Fail | Fail |
| 관련 결함 | 연결 | BUG-011 |

### ID 체계 예 (이 프로젝트)

```
TC - API   - ORDER - 001
     ↑       ↑       ↑
   테스트   기능    일련번호
   레벨    영역

TC-API-SIGNUP-006   API / 회원가입 / 6번
TC-UI-E2E-001       UI / E2E 시나리오 / 1번
TC-EXT-AUTH-002     외부 API / 인증 / 2번
```

**ID는 절대 재사용하지 않는다.** 케이스를 삭제해도 번호는 비워둔다.
결함 리포트나 회의록에 남은 ID가 다른 케이스를 가리키면 추적이 무너진다.

## 3. 자동화 코드에서의 테스트케이스

이 프로젝트는 문서와 코드를 분리하지 않고 **테스트 제목에 TC ID와 기법을 박아** 두었다.

```ts
test('TC-API-SIGNUP-006 | [경계값] 비밀번호 21자 → 400 (상한 경계 바로 위)', async ({ request }) => {
  test.fail(true, 'BUG-001: 비밀번호 최대 길이(20자) 검증 누락으로 21자가 가입된다');

  const res = await request.post('/api/users', {
    data: { email: uniqueEmail('pw'), password: passwordOfLength(21), age: 30 },
    failOnStatusCode: false,
  });

  expect(res.status(), `비밀번호 21자에 대한 응답 코드`).toBe(400);
});
```

이 한 조각에 들어 있는 것

| 요소 | 위치 |
|---|---|
| TC ID | 제목 앞부분 |
| 적용 기법 | `[경계값]` |
| 테스트 조건 | `비밀번호 21자 → 400` |
| 도출 근거 | `(상한 경계 바로 위)` |
| 관련 결함 | `test.fail()` 의 설명 |
| 기대 결과 | `expect(...).toBe(400)` |
| 실패 시 메시지 | `expect` 의 두 번째 인자 |

이렇게 하면 **실행 결과 JSON에서 테스트케이스 명세서를 자동 생성**할 수 있다.
→ `node utils/report-to-csv.js` 가 실제로 그 일을 한다.

## 4. 단언(Assertion) 작성 요령

### 실패 메시지를 남겨라

```ts
// 나쁨 — 실패해도 "expected 400, received 201" 만 나온다
expect(res.status()).toBe(400);

// 좋음 — 어떤 입력에서 실패했는지 바로 보인다
expect(res.status(), `비밀번호 ${len}자에 대한 응답 코드`).toBe(400);
```

데이터 주도 테스트(같은 코드를 값만 바꿔 반복)에서는 **필수**다.
메시지가 없으면 4개 중 어느 케이스가 깨졌는지 로그를 뒤져야 한다.

### 절대값보다 관계를 검증하라

```ts
// 깨지기 쉬움 — 다른 테스트가 재고를 건드리면 실패한다
expect(await shop.stockOf(10)).toBe(18);

// 안정적 — 재고 절대값이 얼마든 "2 줄었다"는 사실은 항상 참이다
const before = await shop.stockOf(10);
await shop.order(null);
expect(await shop.stockOf(10)).toBe(before - 2);
```

### 한 케이스에 여러 단언은 괜찮다 (단, 같은 목적일 때)

```ts
// OK — "할인이 올바르게 적용되었다" 하나를 여러 각도로 확인
expect(body.discount).toBe(5000);
expect(body.finalPrice).toBe(body.totalPrice - 5000);

// 나쁨 — 서로 다른 두 요구사항을 한 케이스에서 검증
expect(body.discount).toBe(5000);        // FR-09-6
expect(cart.items).toEqual([]);          // FR-09-7 → 별도 케이스로 분리
```

앞의 단언이 실패하면 뒤는 실행되지 않는다. 서로 다른 요구사항을 묶으면
**하나가 깨질 때 나머지 상태를 알 수 없다.**

## 5. 테스트 데이터 설계

### 원칙

| 원칙 | 방법 |
|---|---|
| 테스트는 자기 데이터를 **스스로 준비**한다 | 픽스처에서 계정을 새로 생성 |
| 공유 데이터는 **소유권을 정한다** | "상품 ID 10은 재고 검증 테스트 전용" |
| 실행할 때마다 **유일한 값**을 쓴다 | `uniqueEmail()` → UUID 기반 |
| 정리(Cleanup)보다 **격리**가 낫다 | 지우는 대신 안 겹치게 만든다 |

### 이 프로젝트의 실제 사례

```ts
// test-data/minishop.ts
export const PRODUCT = {
  /** 장바구니 담기/삭제 전용. 주문(재고 차감) 금지 */
  CART_ONLY: { id: 1, name: '클린 코드', price: 33000, initialStock: 10 },
  /** 재고 부족 주문(FR-09-2) 검증 전용 */
  LOW_STOCK: { id: 9, name: '데이터 중심 애플리케이션 설계', price: 42000, initialStock: 4 },
};
```

주석에 **"누가 쓰는 데이터인가"** 를 명시했다.
이걸 안 하면 반년 뒤에 누군가 같은 상품을 다른 테스트에서 주문하고,
원인 모를 간헐 실패가 시작된다.

## 6. 테스트케이스 리뷰 체크리스트

- [ ] 요구사항 항목이 전부 최소 1개 이상의 TC로 커버되는가 (추적성 매트릭스)
- [ ] 유효/무효 클래스가 모두 있는가
- [ ] 경계값(min-1, min, max, max+1)이 빠짐없이 있는가
- [ ] 상태를 가진 기능에 상태 전이 케이스가 있는가
- [ ] 불법 전이·권한 위반 케이스가 있는가
- [ ] 기대결과가 판정 가능한 형태로 쓰였는가
- [ ] 다른 케이스에 의존하지 않는가
- [ ] 중복된 케이스가 없는가 (같은 코드 경로를 여러 번)
- [ ] 실행 순서를 바꿔도 결과가 같은가
