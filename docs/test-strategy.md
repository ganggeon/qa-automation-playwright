# MiniShop 테스트 전략

## 1. 주요 위험과 우선순위

점수 = 가능성(1~3) × 피해(1~3)

### 위험 1
- 위험: 잠긴 계정으로도 로그인됨
- 가능성: 3
- 가능성 이유:실패 횟수 설정을 잘못해서 회수가 저장되지 않거나, 5회에 잠기지 않거나, 로그인 시 잠금을 확인하지 않을 가능성이 있음
- 피해: 3
- 피해 이유: 비밀번호를 계속 바꿔 넣어 맞히는 공격을 막는 장치이므로, 이것이 뚫리면 계정을 빼앗기고 그 결과로 개인정보·주문 내역의 유출로 이어질 수 있음

### 위험 2
- 위험:품절된 상품이 장바구니에 추가가 되거나, 남은 재고보다 합산이 많음
- 가능성: 2
- 가능성 이유: 이미 담긴 수량과 새로 담는 수량을 합친 값을 재고와 비교해야 하는데, 새로 담는 수량만 비교하는 실수를 하기 쉬움
- 피해: 2
- 피해 이유: 결제 단계로 넘어가지 않음

### 위험 3
- 위험: 쿠폰 할인 금액이 규칙과 다르게 계산됨 (유효기간·최소 주문금액·0원 미만 처리)
- 가능성: 3
- 가능성 이유: 확인할 조건이 여러 개이고 경계에서 판정이 갈리는 규칙(마지막 날 23:59:59, 금액이 딱 같을 때)이 많아서 실수하기 쉬움
- 피해:3
- 피해 이유: 유효 기간을 넘긴 쿠폰에 적용되어 결제까지 될 경우 비용 문제가 발생. 

## 2. 검증 범위

### 이번에 확인하는 것
- 로그인 FR-02-1~4 — API로 규칙 4개 검증, 화면에서 로그인 성공/실패 확인

### 확인하지 않는 것

#### 제외 1
- 제외: 쿠폰 할인 금액 계산 (위험 3, 9점)
- 이유: 이번 검증은 한 명이 짧은 기간에 하므로 최우선 하나만 깊게 봄. 잠금 우회는 계정·개인정보가 새면 되돌릴 수 없지만, 쿠폰 금액 오류는 주문 기록이 남아 사후 정산이 가능하므로 로그인을 먼저 함. 쿠폰은 규칙이 7개에 결정표까지 있어 별도 검증 회차가 필요
- 남은 위험: 높음 — 유효기간·최소 주문금액·0원 처리 규칙이 검증되지 않은 채 남음. 출시 전 별도 검증이 필요하고, 못 하면 출시 후 주문 금액을 모니터링해야 함

#### 제외 2
- 제외: 장바구니 재고 합산 (위험 2, 4점)
- 이유: 점수가 가장 낮고, 주문할 때 재고를 다시 확인(FR-09-2)하므로 장바구니가 틀려도 잘못된 주문까지는 가지 않음
- 남은 위험: 중간 — 담기 단계에서 고객 불편·문의 가능

## 3. 시작 조건 · 종료 조건

### 시작 조건
- 전용 설정으로 서버가 뜸(초기화 API를 쓰지 않음)
- SPEC대로 테스트 계정 2개(일반·처음부터 잠긴 계정)가 준비됨
- 검사할 코드 버전(SHA)이 정해짐

### 종료 조건
- FR-02-1~4 테스트를 모두 실행함
- 실패마다 원인(알려진 결함 / 새 결함 / 테스트 코드 오류)을 분류함
- 결과를 코드 버전(SHA)과 함께 기록함
- 통과 여부와 출시 권고는 종료 조건이 아니라 릴리스 판단에서 다룸

## 4. 알려진 결함 처리 원칙

### 테스트에서의 표시
- 알려진 결함이 있는 테스트는 "실패 예상"으로 표시하되, 기대한 방식으로 실패했는지까지 확인함
- 다른 이유로 실패하면 새 문제로 봄
- 예상과 달리 통과하면 결함이 고쳐졌는지 확인한 뒤 표시를 해제함

### 출시 판단
- 1절의 피해 점수로 판단함
- 피해 3(보안·돈·되돌릴 수 없음)에 해당하면 알려진 결함이라도 출시를 막음
- 그보다 낮으면 우회 방법과 영향 범위를 적고 출시할 수 있음
