# QA 면접 예상 질문 정리

> 답변은 **이 프로젝트의 실제 사례**로 뒷받침한다.
> 개념만 말하면 외운 티가 나고, 사례가 붙으면 경험으로 들린다.

---

## A. 기본 개념

### Q1. QA와 QC, Testing의 차이는?
**QA는 예방(프로세스), QC는 검출(산출물 검사), Testing은 QC의 수단**입니다.
QA는 "결함이 안 생기게 하는 활동"이라 코드리뷰 규칙 수립이나 DoD 정의도 포함되고,
QC는 만들어진 것에서 결함을 찾는 활동입니다.

> 사례: 이 프로젝트에서 결함 15건 중 9건이 "입력값 검증 누락/경계 오류"였습니다.
> 이건 QC(테스트)로 잡은 결과지만, QA 관점에서는 **코드리뷰 체크리스트에
> "상한값도 검사했는가"를 추가하자**는 개선 제안으로 이어집니다.

### Q2. 심각도와 우선순위의 차이는?
심각도는 **기술적 영향**(QA가 판단), 우선순위는 **언제 고칠지**(PO가 판단)입니다.
높은 심각도-낮은 우선순위(관리자 전용 화면의 데이터 손상)나
낮은 심각도-높은 우선순위(대외 발표 전날 로고 오탈자) 조합이 실제로 존재합니다.

### Q3. 재확인 테스트와 회귀 테스트의 차이는?
**재확인(Confirmation)은 고친 그 결함 하나**, **회귀(Regression)는 그 수정 때문에
다른 데가 깨지지 않았는지**입니다. 자동화의 핵심 가치가 회귀 테스트예요 —
손으로는 매 릴리스마다 168건을 돌릴 수 없으니까요.

### Q4. 테스트 7원칙 중 실무에서 가장 와닿은 것은?
**"결함은 집중된다"** 와 **"살충제 역설"** 입니다.

> 사례: 이 프로젝트에서 주입 결함 15건 중 6건이 경계값 처리(`<` vs `<=`)에 몰려 있었습니다.
> 처음에는 "상한을 빼먹는 패턴"이라고 정리했는데, **결함 목록을 다시 세어 보니 틀렸습니다.**
> 상한 누락은 2건이고 하한 쪽이 3건이었어요. 방향이 쏠린 게 아니라
> **어느 쪽이든 한쪽 끝이 빈다**는 게 실제 패턴이었습니다(6건 중 5건).
> 그래서 "상한을 더 보자"가 아니라 **"네 점을 기계적으로 다 찍자"** 로 결론을 바꿨습니다.
> 요약을 먼저 쓰고 데이터를 나중에 맞추면 이런 착각이 생긴다는 것도 같이 배웠습니다.

## B. 테스트 설계

### Q5. 로그인 기능을 테스트한다면 어떤 케이스를 만들겠습니까?
기법별로 나눠서 답합니다.

- **동등분할**: 올바른 계정 / 비밀번호 불일치 / 없는 계정 / 빈 값
- **경계값**: 비밀번호 길이 min-1, min, max, max+1
- **상태 전이**: 실패 누적 → 계정 잠금. 4회 실패 후 성공하면 카운트 초기화,
  5회째 실패 시 잠금, **잠긴 계정은 올바른 비밀번호로도 거부**
- **보안**: 없는 계정과 비밀번호 불일치의 응답이 구분되면 계정 존재 여부가 새어나감
- **토큰 생명주기**: 로그아웃 후 토큰 재사용 시 401

> 사례: 마지막 두 개에서 실제 결함이 나왔습니다.
> 5회 실패 후에도 잠기지 않았고(BUG-004), 로그아웃한 토큰이 계속 유효했습니다(BUG-005).
> 둘 다 **단발 요청으로는 못 잡고 순서가 있는 요청 연속으로만** 잡히는 결함입니다.

### Q6. 경계값 분석을 실제로 어떻게 적용했나요?
유효 구간이 min~max면 **min-1, min, max, max+1** 네 점을 기계적으로 검증합니다.

> 사례: 비밀번호 길이 8~20 규칙에서 7/8/20/21을 테스트했더니
> 앞의 세 개는 통과하고 **21자만 실패**했습니다.
> 개발자가 `if (pw.length < 8)` 만 쓰고 상한 검사를 빼먹은 거죠.
> 하한만 봤다면 절대 못 잡았을 결함입니다.
> 이 프로젝트에서 경계값 분석만으로 결함 5건(전체의 1/3)을 잡았습니다.

### Q7. 결정표는 언제 쓰나요? 한계는?
조건 여러 개가 조합되어 결과가 갈릴 때 씁니다.

> 사례: 주문 기능에 조건이 5개(장바구니 비었나, 쿠폰 입력됐나, 존재하나,
> 유효기간 내인가, 최소금액 이상인가)라 이론상 32가지 조합인데,
> 앞 조건에서 걸리면 뒤는 무관(`-`)이므로 **규칙 6개로 압축**했습니다.

**한계**는 명확합니다. 결정표는 조건의 Y/N만 봐요.
"주문금액 ≥ 최소금액"이 Y인지 N인지는 보지만 **정확히 같을 때 어느 쪽인지**는 안 봅니다.
그래서 경계값과 반드시 같이 씁니다.

> 실제로 결정표 6건은 전부 통과했는데,
> 경계값으로 "정확히 30,000원" 케이스를 넣으니 결함이 나왔습니다(BUG-011).
> 개발자가 `>=` 를 `>` 로 구현했더군요.

### Q8. 테스트케이스를 다 만들 수는 없는데 어떻게 우선순위를 정하나요?
**리스크 기반**으로 정합니다. 축은 두 개예요.
- **영향도**: 금전 손실 / 데이터 손상 / 보안 > 기능 오류 > 표시 오류
- **발생 가능성**: 복잡한 로직, 최근 변경된 코드, 과거 결함이 많았던 모듈

> 사례: 이 프로젝트에서 금액 계산(주문/쿠폰)에 가장 많은 케이스를 배치했고,
> 실제로 Critical 5건 중 2건이 거기서 나왔습니다.

## C. 자동화

### Q9. 무엇을 자동화하고 무엇을 안 하나요?
**반복되고, 판정이 명확하고, 오래 살아남을 것**을 자동화합니다.
회귀 테스트, 데이터 조합이 많은 검증, API 계약 검증, 크로스 브라우저.

**안 하는 것**: 탐색적 테스트, 사용성 판단, 요구사항이 계속 바뀌는 신규 기능,
1회성 검증. 자동화율 100%는 목표가 아닙니다 — 한 번 쓰고 버릴 테스트를
자동화하면 순손실이에요.

### Q10. UI 테스트와 API 테스트 비중을 어떻게 가져가나요?
테스트 피라미드대로 **API를 두껍게**, E2E는 얇게 가져갑니다.

> 사례: 이 프로젝트는 API 89건 / UI 통합 15건 / E2E 3건입니다.
> "비밀번호 8자 경계"는 API에서만 보고, UI에서는 "실패 메시지가 뜨는가"만 확인합니다.
> 같은 검증을 두 레벨에서 반복하면 유지보수 비용만 두 배가 되니까요.

**API 테스트만 잡을 수 있는 것도 있습니다.** UI는 `<input type="number">` 로
음수를 막을 수 있지만 API는 누구나 직접 호출합니다.
실제로 수량 `-3`을 API로 보내니 그대로 담기고 총액이 음수가 됐습니다(BUG-008).
UI만 테스트했다면 못 잡았을 결함입니다.

### Q11. Flaky 테스트를 만나면 어떻게 하나요?
**재시도로 덮지 않습니다.** `retries` 를 올리는 건 문제를 숨기는 거예요.
원인을 찾을 때까지 격리하고 조사합니다.

자주 나오는 원인: 명시적 sleep, 테스트 간 데이터 공유, 절대값 단언, 자원 경합.

> 사례: 전체 프로젝트를 한 번에 돌렸더니 Firefox 6건이 40~60초 타임아웃으로
> 실패했습니다. 처음엔 브라우저 호환성을 의심했는데, **Firefox 단독으로 돌리니
> 19건 전부 통과**했습니다. 원인은 자원 경합이었어요 —
> 워커 9개 × 브라우저 3종이 동시에 뜨고 단일 스레드 SUT까지 같은 PC에서 도니까요.
> **워커 2개로 재실행해 19건 전부 통과**하는 걸 확인하고, CI는 그 실험값 2로,
> 로컬은 속도를 감안해 4로 상한을 뒀습니다. 경위는 설정 파일 주석에 남겼습니다.
>
> **"가끔 실패한다"의 원인이 항상 테스트 코드는 아니다**는 걸 배웠습니다.

### Q12. 테스트 격리는 어떻게 보장했나요?
처음엔 "매 테스트 전 서버 전체 초기화"를 생각했는데, **병렬 실행과 충돌**합니다.
내가 초기화하는 순간 옆 워커의 테스트가 죽어요.

그래서 **테스트마다 새 계정을 생성**하는 방식으로 갔습니다.
장바구니와 주문은 계정별로 분리돼 있으니 이것만으로 격리가 성립하고 병렬도 안전합니다.

전역 상태인 **재고**는 두 가지로 처리했습니다.
1. "이 상품은 이 테스트 전용"이라고 **소유권을 명시**
2. 절대값(`toBe(18)`) 대신 **변화량**(`toBe(before - 2)`)으로 검증

### Q13. 미수정 결함이 있으면 CI가 계속 빨간불인데 어떻게 하나요?
Playwright의 `test.fail()` 로 **알려진 결함**이라고 표시합니다.

```ts
test.fail(true, 'BUG-013: 결제금액 하한 처리가 없어 음수 결제금액이 생성된다');
```

이렇게 하면 세 가지가 동시에 됩니다.
1. **CI가 초록불로 유지된다** — 빨간불이 방치되면 팀이 실패에 무뎌집니다
2. **결함이 코드에 문서화된다** — 별도 문서와 코드가 따로 놀지 않습니다
3. **결함이 수정되면 자동으로 알려준다** — 통과해버리면
   `Expected to fail, but passed` 로 실패합니다. 마킹을 지우라는 신호죠

`test.skip()` 은 안 씁니다. 스킵된 테스트는 아무도 다시 안 봅니다.

### Q14. Page Object Model의 원칙은?
**페이지 객체는 검증하지 않습니다.** `expect` 를 넣는 순간 재사용이 안 돼요 —
성공을 기대하는 테스트와 실패를 기대하는 테스트가 같은 메서드를 못 씁니다.

페이지 객체는 "무엇을 할 수 있는가"와 "무엇이 보이는가"만 제공하고,
"무엇을 검증하는가"는 테스트가 담당합니다.

## D. 협업

### Q15. 개발자가 "재현 안 됩니다"라고 하면?
먼저 제 리포트를 의심합니다. 대개 **환경이나 데이터 조건이 빠져** 있어요.

1. 재현 절차에 구체적 값이 있는지 확인 (상품명, 금액, 계정)
2. 환경 정보 확인 (버전, 브라우저, 데이터 상태)
3. **증거를 첨부** — Playwright trace 파일에는 DOM 스냅샷, 네트워크 요청,
   콘솔 로그가 전부 들어 있어서 "제 PC에선 되는데요"가 성립하지 않습니다
4. 그래도 안 되면 같이 앉아서 재현합니다

재현율이 낮으면 솔직히 "3/10 재현"이라고 적습니다. 숨기면 신뢰를 잃어요.

### Q16. 개발자가 결함을 Rejected 하면?
감정적으로 대응할 일이 아니고 셋 중 하나입니다.
1. **제가 명세를 잘못 읽었다** → 인정하고 닫습니다
2. **명세 자체가 모호하다** → 명세를 고치자고 제안합니다. 이게 진짜 QA의 기여예요
3. **개발자가 명세를 잘못 읽었다** → 요구사항 번호를 인용해 근거를 댑니다

결함 리포트는 비난이 아니라 정보 전달입니다.
"당신이 틀렸다"가 아니라 "명세와 구현이 어긋난 지점이 여기입니다"로 씁니다.

### Q17. 릴리스 일정이 촉박한데 결함이 남았다면?
**릴리스 여부는 제가 결정하지 않습니다.** QA는 **판단 근거를 제공**합니다.

- 잔존 결함을 심각도별로 정리
- 각 결함의 **비즈니스 영향**을 구체적으로 (몇 명이, 어떤 상황에서, 얼마나)
- 우회 방법이 있는지
- 미수정 시 리스크

> 사례: 이 프로젝트의 요약보고서에서 "릴리스 불가(No-Go)"를 권고했지만,
> 근거를 이렇게 제시했습니다 — Critical 5건 중 BUG-013은 결제금액이 음수(-47,655원)로
> 계산되어 **PG 연동 시 고객에게 돈을 지급하는** 상황이 될 수 있고,
> BUG-015는 저장형 XSS라 **목록을 보는 모든 사용자**에게 영향이 갑니다.
>
> 최종 결정은 PO가 하되, 그 결정이 정보에 기반하도록 만드는 게 제 일입니다.

## E. 이 프로젝트에 대해

### Q18. 이 포트폴리오에서 무엇을 보여주고 싶었나요?
세 가지입니다.

1. **명세에서 테스트케이스를 도출하는 능력** — 코드를 보고 만든 게 아니라
   요구사항 명세만 보고 설계했습니다. 그래서 구현이 틀린 경우를 잡을 수 있었습니다
2. **자동화 구현 능력** — API 89건 + UI 18건 × 3브라우저, POM, 픽스처, CI
3. **결과를 QA 산출물로 전달하는 능력** — 테스트 계획서부터 요약 보고서까지

### Q19. 자기가 만든 SUT에서 결함을 찾은 건 의미가 있나요?
날카로운 지적이고, **저도 그 한계를 인지하고 있습니다.**
자기가 심고 자기가 찾은 결함의 검출률 100%는 실력의 증거가 못 됩니다.

그래서 **남이 만든 공개 API(restful-booker)** 를 공식 문서와 REST 규약에 대조해
독립적으로 결함 5건을 찾았습니다.
- 인증 실패에 200 OK 반환
- 리소스 생성에 201이 아닌 200
- 삭제 성공에 `201 Created`
- 체크아웃이 체크인보다 빠른 예약이 그대로 생성됨
- **필수 필드 누락 시 400이 아니라 500** ← 이게 가장 심각합니다

자체 SUT는 "설계 기법을 체계적으로 적용하는 과정"을 보여주는 용도이고,
외부 API는 "실제로 결함을 찾을 수 있는가"를 보여주는 용도로 나눴습니다.

### Q20. 이 프로젝트에서 가장 어려웠던 점은?
**테스트 격리와 병렬 실행의 균형**이었습니다.

처음엔 매 테스트 전에 서버를 초기화했는데, 병렬로 돌리니 서로를 죽이더군요.
계정 격리로 바꿨더니 이번엔 **전역 상태인 재고** 때문에 간헐 실패가 났습니다.
그래서 상품별 소유권을 정하고 검증을 변화량 기준으로 바꿨습니다.

그리고 **테스트 코드 자체의 버그**도 겪었습니다.
이메일을 `Date.now() + 카운터` 로 만들었는데, 병렬 워커는 별도 프로세스라
카운터가 각자 0부터 시작합니다. 같은 밀리초에 같은 번호가 나와서
중복 가입(409)으로 실패했어요. UUID로 바꿔 해결했습니다.

> **테스트 코드도 코드고, 코드에는 버그가 있다**는 걸 체감했습니다.
