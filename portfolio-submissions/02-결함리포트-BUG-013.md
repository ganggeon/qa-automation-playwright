## [BUG-013] 할인액이 주문금액보다 크면 결제금액이 음수(-47,655원)로 표시된다

| 항목 | 내용 |
|---|---|
| 심각도 / 우선순위 | **Critical / P1** — 이 프로젝트 [테스트 계획서](../artifacts/01-테스트계획서.md)의 심각도 기준에 **음수 결제금액**이 Critical 예시로 정의돼 있어 그대로 적용했다. 본인이 확인한 범위는 아래 「확인 범위」까지다 |
| 위반 요구사항 | **FR-09-5** |

| 발견 TC | `TC-UI-E2E-003` |
| 환경 | MiniShop v1.0 / Chromium(Desktop Chrome) / Windows 11 |
| 재현율 | 100% (대기 조건 추가 후 1/1) |
| 상태 | **Closed** (2026-09-07 수정·재확인 — 아래 「상태 갱신」 참조) |

### 재현 절차

1. `qa@test.com` / `Qa123456` 으로 로그인한다
2. **'북마크 세트'(2,345원)** 를 1개 장바구니에 담는다
3. 장바구니에서 쿠폰 코드 **`BIG50000`**(50,000원 할인)을 입력하고 **[주문하기]** 를 누른다
4. 화면 상단 메시지의 결제금액을 확인한다

### 기대 결과

> **FR-09-5** — 할인 후 결제금액(`finalPrice`)은 **0원 미만이 될 수 없다.**
> 할인액이 총액보다 크면 0원으로 처리한다.

화면에 `결제금액 0원` 이 표시되어야 한다.

### 실제 결과

화면 상단 메시지에 음수 금액이 그대로 노출된다.

```
주문이 완료되었습니다. 주문번호 1 / 결제금액 -47,655원
```

> 증거 화면(주문번호가 정상 발급된 상태에서 결제금액이 음수로 표시)은 포트폴리오 PDF 6쪽에 수록했다. 그 화면은 **AI 튜터가 작성한 임시 재현 테스트**로 확보한 것이다.

### 확인 범위 — 어디까지 확인했고 어디부터 확인하지 않았는가

- 확인한 것: **주문 완료 화면의 표시**까지.
- 확인하지 않은 것: **API 응답 값**과 **저장된 주문 레코드**.
- 확인한 재현 조합: **2,345원 상품 + `BIG50000` 쿠폰 1건**. 다른 금액·쿠폰 조합은 확인하지 않았다.
- MiniShop은 **결제 연동이 미구현인 학습 환경**이므로, 실제 지급이나 금전 손실이 발생한 것은 아니다.

### 잠재 영향 — 같은 결함이 실제 서비스에 있다면

- **재무·정산** — 음수 금액 주문이 매출 집계에 섞일 수 있다. 환불·적립 로직이 결제금액을 참조하면 손실로 이어질 수 있다.
- **고객지원(CS)** — 주문번호는 정상 발급되었는데 금액이 음수다. 처리할 표준 절차가 없으면 건건이 수동 정정해야 한다.
- **데이터** — 잘못된 금액이 저장되었다면 코드를 고쳐도 기존 주문 레코드는 복구되지 않아 별도 정정 작업이 필요하다.
- **영향 범위를 확정하려면** API 응답과 저장값, 결제·정산 연동 여부를 추가로 확인해야 한다. 위 세 항목은 그 확인 전까지는 **가능성**이다.

### 원인 분석

확신할 때만 적고, 모르면 비워 둔다. 틀린 원인을 적으면 개발자가 QA의 실수로 판단하고 결함 자체를 넘길 수 있다.

## 상태 갱신 — BUG-013 Closed (2026-09-07)

| 항목 | 내용 |
|---|---|
| 수정 위치 | `sut/server.js:287~289` (`[SEED-13]` 자리) |
| 수정 내용 | `discount = Math.min(discount, totalPrice)` + `finalPrice = Math.max(0, totalPrice - discount)` |
| 확인 테스트 | `TC-API-ORDER-003`, `TC-UI-E2E-003` — 둘 다 `Expected to fail, but passed` 확인 후 `test.fail()` 삭제 |
| 회귀 | `--project=api --project=ui` **112 passed / 0 failed**, typecheck OK<br>※ 112건은 API·UI(Chromium) **부분 회귀**다. 3개 브라우저와 외부 사이트를 포함한 176건 전체 회귀는 이후 따로 실행했다 |

### 확인 과정에서 배운 것 — 단언을 추가하기 전에 기대값의 근거를 확인한다

`finalPrice`만 막고 `discount`를 안 막아도 **두 확인 테스트는 모두 통과한다.**
어느 테스트도 `discount`를 보지 않기 때문이다.
(할인 제한 한 줄을 빼고 다시 실행한 실측은 AI 튜터가 보여 준 것이다.)

이후 `TC-API-ORDER-003`에 `expect(body.discount).toBe(2345)` 단언이 추가되었다.

**다만 2026-09 재검토에서 확인한 것** — 그 기대값(할인액을 총액까지만)은 **참고 산출물에 있던 값**이고,
이 리포트의 「기대 결과」에는 `discount` 칸이 없었다.
**FR-09-5는 결제금액(`finalPrice`)의 0원 하한만 규정할 뿐, 저장·반환되는 할인액 필드의 상한은 명시하지 않는다.**

→ 그러므로 여기서 얻을 교훈은 "기대 결과 표 전체를 덮어야 한다"가 아니라,
**단언을 추가하기 전에 그 기대값이 어떤 명세나 합의에 근거하는지부터 확인해야 한다**는 것이다.
근거가 명세에 없으면, 단언을 넣기 전에 "이 값이 규칙인지"를 먼저 물어야 한다.

### 이 저장소에 아직 남아 있는 것 (2026-09-15 확인)

정직하게 밝혀 둔다. 위 재검토는 **문서에만 반영했고 코드에는 아직 반영하지 않았다.**

- `tests/api/05-order.spec.ts`의 `TC-API-ORDER-003`에는 `expect(body.discount).toBe(2345)` 단언과
  "리포트의 기대 결과 표에 있던 칸이므로 확인 테스트도 이 칸을 덮어야 한다"는 주석이 그대로 있다.
  **이 리포트의 기대 결과에는 `discount` 칸이 없다** — 그 값은 참고 산출물 쪽에 있던 것이다.
- 할인액 필드의 상한이 실제로 요구사항인지는 **명세로 확정되지 않았다.** 명세 담당자에게 확인할 항목이다.
- 따라서 이 단언은 확정된 요구사항이 아니라 **참고 산출물에서 가져온 가정**으로 읽어야 한다.
