**경계값 처리 오류 6건의 방향 분석**

| 방향 | 건수 | 결함 |
|---|---:|---|
| 상한 검증 누락 | 2 | BUG-001(비밀번호 21자), BUG-002(나이 121) |

> 초안에서는 이 6건을 **"상한 검증 누락 4건 — 하한은 잘 챙기고 상한을 빼먹는 패턴"** 이라고
> 요약했다. **결함 목록을 다시 세어 보니 틀린 서술이었다.** 상한 누락은 2건이고
> 오히려 하한 쪽이 3건이다. 실제 패턴은 방향이 아니라 **"어느 쪽이든 한쪽 끝이 빈다"**(6건 중 5건)이다.
>
> 시사점도 달라진다. "상한을 조심하라"가 아니라 **"min·max 어느 한쪽만 확인하는 것은 의미가 없다.
> 네 점(min-1, min, max, max+1)을 다 찍어야 한다"** 가 옳은 결론이다.
> 요약을 먼저 쓰고 데이터를 나중에 맞추면 이런 일이 생긴다.

## 4. 테스트 품질 자체에 대한 평가

### 4.1 결함 검출 효율 (DDE)

SUT에 **15건의 결함을 의도적으로 주입**하고 테스트 설계는 명세(SPEC.md)만 보고 진행했다.

$$\text{DDE} = \frac{15}{15} \times 100 = 100\%$$

다만 이 수치는 **자기가 심고 자기가 찾은** 것이므로 절대적 지표로 볼 수 없다.
객관적 검증을 위한 근거는 다음 두 가지다.

| 근거 | 내용 |
|---|---|
| 외부 API 교차 검증 | **남이 만든 공개 API(restful-booker)** 를 공식 문서·REST 규약에 대조해 결함 5건 검출 |
| **비주입 결함 검출** | 정답지에 없던 **BUG-016**(합산 시 수량 상한 미검사)을 명세 정독만으로 검출 |

**DDE 100%의 함정.** 이 수치는 "심은 유형의 결함"에 한해 100%라는 뜻이다.
심지 않은 유형은 애초에 분모에 없다. BUG-016 이 속한 "검증 적용 지점 오류"는
주입 목록에 없던 유형이었고, 그래서 DDE 로는 영원히 드러나지 않는다.
**DDE 를 품질 지표로 인용할 때는 이 단서를 반드시 함께 말해야 한다.**

### 4.2 안정성

| 항목 | 결과 |
|---|---|
| 전체 재실행 시 Fail | 0건 |
| Flaky 테스트 | 0건 (조사 및 조치 완료 — 아래) |
| 로컬 재시도 설정 | 0회 (문제를 숨기지 않기 위함) |

**Flaky 조사 기록**
전체 프로젝트 동시 실행 시 Firefox 6건이 40~60초 타임아웃으로 실패했다.
단독 실행에서는 전부 통과하여 코드 문제가 아닌 **자원 경합**으로 판단했다.

| 단계 | 내용 |
|---|---|
| 재현 | 기본 워커 수(코어수/2 = 9)로 6개 프로젝트 동시 실행 → Firefox 6건 타임아웃 |
| 실험 | **워커 2개**로 같은 테스트 재실행 → 19건 전부 통과 |
| 적용 | `workers: process.env.CI ? 2 : 4` — CI는 실험값 2, 로컬은 속도를 감안해 4 |

경위는 `playwright.config.ts` 주석에 기록.

**잠재 Flaky 1건 사전 제거 (BUG-016 작업 중 발견)**
`TC-API-CART-004`(수량 99 담기)가 재고 100짜리 상품을 다른 주문 테스트 3종과
공유하고 있었다. 지금은 BUG-009(담기 시 재고 미확인) 때문에 재고와 무관하게 통과하지만,
**그 결함이 수정되면 재고 부족으로 실패**하고 실행 순서에 따라 결과가 흔들린다.
재고 999짜리 수량 검증 전용 상품(id 16)을 추가해 해소했다.

> **결함 덕분에 통과하는 테스트는 회귀 자산이 아니다.** "지금 초록불"이라는 사실만으로는
> 안정성을 증명할 수 없고, "결함이 고쳐져도 초록불인가"까지 봐야 한다.

| **입력값 검증 체크리스트를 코드리뷰 항목에 추가** | MiniShop 결함 16건 중 10건이 "검증 누락/경계 오류". 체크 항목은 "상한도 검사했는가"가 아니라 **"min·max 양쪽을 다 검사했는가"** 여야 한다(하한 누락이 더 많았다) |
| **검증 위치를 "요청 시점"이 아니라 "상태 변경 시점"으로 통일** | BUG-016. 검사식이 있어도 적용 지점이 틀리면 무력화된다. 누적·병합이 일어나는 로직은 계산 결과를 다시 검증해야 한다 |
| **금액 계산 로직에 하한/절사 규칙 명문화** | BUG-012, 013 모두 금액 계산. 공통 유틸 함수로 추출 권장 |
| **출력 인코딩을 프레임워크 레벨에서 강제** | BUG-015는 `innerHTML` 을 쓰는 한 반복된다. 렌더링 헬퍼로 통일 필요 |

### 6.2 명세

| 제안 | 근거 |
|---|---|
| "이상/이하/초과/미만"을 명세에 명시적으로 표기 | BUG-011은 `≥`를 `>`로 구현한 결함. 명세가 "30,000원 이상"이라고 썼는데도 발생했으므로 코드리뷰 시점의 확인 항목으로도 넣을 것 |
| 오류 코드 목록을 명세에 표로 관리 | 클라이언트가 분기 처리할 수 있도록 |
| **명세 리뷰를 테스트 설계보다 앞에 배치** | 명세 결함 6건 중 2건(`createdAt` 누락, 상품 마스터 누락)이 테스트를 다 만든 뒤에 발견돼 테스트 코드까지 되돌려 고쳤다. 상세: [06-명세결함리포트.md](06-명세결함리포트.md) |
| **한 문장에 조건이 두 개면 규칙을 쪼개 번호를 붙일 것** | FR-06-4가 "합산한다 + 합산 결과도 규칙을 지킨다" 두 조건인데 한 문장이라 뒷 조건이 누락됐다(BUG-016) |
