## 4. 테스트 품질 자체에 대한 평가

### 4.1 결함 검출 효율 (DDE)

MiniShop에는 **명세 위반 15곳이 학습 환경에 의도적으로 주입**됐다(1곳은 이후 수정).
SUT·명세·테스트 스위트 대부분은 Claude가 같은 학습 환경에서 구성했으므로,
테스트 설계가 주입 정보를 모르는 독립적인 조건에서 진행됐다고 볼 근거는 없다.

DDE = 검출된 주입 결함 15건 / 전체 주입 결함 15건 × 100 = 100%

이 수치는 **주입 목록에 대한 누적 검출률**이다. 동일한 학습 환경에서 구성된 결과이므로
학습자의 독립적인 발견 역량이나 제품 전체의 품질을 증명하지 않는다. 보완 사례는 다음과 같다.

| 근거 | 내용 |
|---|---|
| 외부 API 검증 | 공개 API(restful-booker)를 공식 문서·API 관례에 대조한 결과: **관례 위반·개선 제안 4건 + 명확한 결함 1건(필수 필드 누락 시 500)** |
| **비주입 결함 검출** | **BUG-016**(합산 시 수량 상한 미검사)은 학습 시작 전(2026-08-03) Claude·Codex의 사전 검토에서 발견됐다 |

**DDE 100%의 함정.** 이 수치는 "심은 유형의 결함"에 한해 100%라는 뜻이다.
심지 않은 유형은 애초에 분모에 없다. BUG-016 이 속한 "검증 적용 지점 오류"는
주입 목록에 없던 유형이었고, 그래서 DDE 로는 영원히 드러나지 않는다.
**DDE 를 품질 지표로 인용할 때는 이 단서를 반드시 함께 말해야 한다.**

### 4.2 안정성

| 항목 | 결과 |
|---|---|
| 전체 재실행 시 Fail | 0건 (2026-09-09 전체 실행) |
| Flaky 테스트 | 0건 (2026-09-09 실행에서 관찰된 결과, 과거 타임아웃 원인은 아래 추정) |
| 로컬 재시도 설정 | 기본 0회, 외부 프로젝트는 2회 |

**Flaky 조사 기록**
전체 프로젝트 동시 실행 시 Firefox 6건이 40~60초 타임아웃으로 실패했다.
단독 실행에서는 전부 통과했고, 워커를 2개로 줄인 실행에서도 통과했다.
이 관찰을 근거로 **자원 경합을 원인으로 추정**했으며, 코드나 다른 환경 요인이 배제된 것은 아니다.

| 단계 | 내용 |
|---|---|
| 재현 | 기본 워커 수(코어수/2 = 9)로 6개 프로젝트 동시 실행 → Firefox 6건 타임아웃 |
| 실험 | **워커 2개**로 같은 테스트 재실행 → 19건 전부 통과 |
| 적용 | `workers: process.env.CI ? 2 : 4` — CI는 실험값 2, 로컬은 속도를 감안해 4 |

관찰과 워커 설정은 `playwright.config.ts`에 기록되어 있으며, 원인에 대한 설명은 추정으로 해석해야 한다.

**잠재적인 테스트 간섭 완화 (2026-08-03 Claude·Codex 사전 검토)**
`TC-API-CART-004`(수량 99 담기)가 재고 100짜리 상품을 다른 주문 테스트 3종과
공유하고 있었다. 당시에는 BUG-009(담기 시 재고 미확인) 때문에 재고와 무관하게 통과했지만,
그 결함이 수정되면 공유 재고가 먼저 차감될 경우 재고 부족으로 실패할 수 있었다.
이 위험을 줄이기 위해 당시 검토에서 재고 999짜리 수량 검증 전용 상품(id 16)이 추가됐다.

> **결함 덕분에 통과하는 테스트는 회귀 자산이 아니다.** "지금 초록불"이라는 사실만으로는
> 안정성을 증명할 수 없고, "결함이 고쳐져도 초록불인가"까지 봐야 한다.

**릴리스 불가 (No-Go).**

**MiniShop 잔존 결함 수정 요청 순서**

BUG-013(음수 결제금액)은 2026-09-07 수정·재확인되어 요청 대상에서 제외한다.

| 4 | BUG-005 (로그아웃 무효) | 세션 탈취 대응 불가 |
| 5~10 | Major 6건 | 이번 릴리스 내 수정 |
| 11~15 | Minor 5건 | 차기 릴리스 반영 가능 |

외부 API는 **Major 1건(EXT-BUG-005: 500 응답) · Minor 4건(EXT-BUG-001~004: 관례 위반·개선 제안)**으로 별도 보고한다.

**BUG-009와 BUG-014는 함께 수정해야 한다.** 원인 계열은 같지만 수정 위치가 다르다
(장바구니 담기 시점 / 주문 확정 시점). 담기에서만 막으면 그 사이에 재고가 줄어든 경우를 놓친다.

**BUG-008·BUG-016도 함께 수정해야 한다.** 둘 다 수량 규칙이지만 걸리는 지점이 다르다.

합산 결과에는 안 걸린 것이다. **요청값과 상태 변경 후의 계산 결과를 각각 검증해야 한다.**

> 릴리스 계획에 반영해야 한다.

## 6. 개선 제안

### 6.1 프로세스

| 제안 | 근거 |
|---|---|
| **입력값 검증 체크리스트를 코드리뷰 항목에 추가** | MiniShop 결함 16건 중 10건이 "검증 누락/경계 오류". 체크 항목은 "상한도 검사했는가"가 아니라 **"min·max 양쪽을 다 검사했는가"** 여야 한다(하한 누락이 더 많았다) |
| **요청값 검증과 상태 변경 결과 검증을 함께 적용** | BUG-008·016. 요청 수량이 유효해도 합산 결과는 상한을 넘을 수 있다. 요청값의 1~99 정수 조건과 합산 후 수량·재고 조건을 각각 검증해야 한다 |
| **금액 계산 로직에 하한/절사 규칙 명문화** | BUG-012, 013 모두 금액 계산. 공통 유틸 함수로 추출 권장 |
| **출력 인코딩을 프레임워크 레벨에서 강제** | BUG-015는 `innerHTML` 을 쓰는 한 반복된다. 렌더링 헬퍼로 통일 필요 |

### 6.2 명세

| 제안 | 근거 |
|---|---|
| "이상/이하/초과/미만"을 명세에 명시적으로 표기 | BUG-011은 `≥`를 `>`로 구현한 결함. 명세가 "30,000원 이상"이라고 썼는데도 발생했으므로 코드리뷰 시점의 확인 항목으로도 넣을 것 |
| 오류 코드 목록을 명세에 표로 관리 | 클라이언트가 분기 처리할 수 있도록 |
| **명세 리뷰를 테스트 설계보다 앞에 배치** | 명세 결함 6건 중 2건(`createdAt` 누락, 상품 마스터 누락)이 테스트를 다 만든 뒤에 발견돼 테스트 코드까지 되돌려 고쳤다. 상세: [06-명세결함리포트.md](06-명세결함리포트.md) |
| **한 문장에 조건이 두 개면 규칙을 쪼개 번호를 붙일 것** | FR-06-4가 "합산한다 + 합산 결과도 규칙을 지킨다" 두 조건인데 한 문장이라 뒷 조건이 누락됐다(BUG-016) |

### 6.3 테스트

| 제안 | 근거 |
|---|---|
| 동시성 테스트 추가 | 마지막 재고 1개를 두 사용자가 동시에 주문하는 경우 미검증. **BUG-014 수정 후 최우선** — 재고 검증이 생기면 그때부터 경쟁 조건이 실제 리스크가 된다 |
| 성능 기준선 측정 | 현재 응답시간 상한 확인은 Postman 컬렉션 1건뿐이고 기준선이 없다 |
| `problem_user` 시나리오 확대 (SauceDemo) | 외부 UI 테스트가 정상 경로에 치우쳐 있다 |
| **커버리지 집계 단위를 "규칙"으로 전환** | 요구사항 단위 100%가 규칙 단위의 공백을 가렸다(§2.3). FR을 규칙 ID 단위로 쪼개 추적할 것 |
| **알려진 결함 TC의 실패 지점·사유까지 점검** | `test.fail()`은 다른 이유로 실패해도 알려진 실패로 집계할 수 있다. `error.code` 단언이 있어도 그 앞에서 실패하면 실행되지 않으므로 실패 지점과 사유를 함께 확인해야 한다 |
