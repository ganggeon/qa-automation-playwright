# 테스트케이스 명세서 — 설계 기법 적용 과정

> 테스트케이스는 "생각나는 대로" 쓰는 게 아니라 **기법으로 도출**한다.
> 이 문서는 요구사항 한 줄에서 테스트케이스가 나오기까지의 과정을 보여준다.
>
> 실행 결과는 [04-테스트수행결과.csv](04-테스트수행결과.csv) 참조.

## 1. 동등분할 (Equivalence Partitioning)

### 원리
입력 가능한 값 전체를 "같은 방식으로 처리될 그룹"으로 나누고, **각 그룹에서 1개씩만** 테스트한다.
비밀번호 8자를 테스트했으면 9자, 10자, 11자를 또 테스트할 이유가 없다. 같은 코드 경로를 탄다.

### 적용 — FR-01-1 이메일 형식

> "이메일은 `로컬부@도메인.최상위도메인` 형식이며, 도메인에 점이 최소 1개 있어야 한다"

| 분할 클래스 | 종류 | 대표값 | 기대 결과 | TC ID |
|---|---|---|---|---|
| 표준 형식 | 유효 | `valid@example.com` | 201 | TC-API-SIGNUP-011 |
| `@` 없음 | 무효 | `no-at-sign.com` | 400 | TC-API-SIGNUP-012 |
| 로컬부 없음 | 무효 | `@example.com` | 400 | TC-API-SIGNUP-013 |
| 도메인에 점 없음 | 무효 | `a@b` | 400 | **TC-API-SIGNUP-014 → BUG-003** |
| 빈 값 | 무효 | `` | 400 | TC-API-SIGNUP-015 |

무효 클래스를 4개나 나눈 이유: **무효 입력은 각각 다른 코드 경로로 처리될 가능성이 높다.**
실제로 `a@b`만 통과하는 결함이 여기서 잡혔다.

### 적용 — FR-04 검색어

| 분할 클래스 | 대표값 | 기대 결과 | TC ID |
|---|---|---|---|
| 표기 일치 | `Java` | 'Java의 정석' 조회됨 | TC-API-PROD-012 |
| 소문자 표기 | `java` | 조회됨 (대소문자 무시) | **TC-API-PROD-013 → BUG-007** |
| 대문자 표기 | `JAVA` | 조회됨 | **TC-API-PROD-014 → BUG-007** |
| 미일치 | `존재하지않는상품` | 0건 | TC-API-PROD-015 |

## 2. 경계값 분석 (Boundary Value Analysis)

### 원리
결함은 구간의 **가장자리**에 몰린다. `<` 와 `<=` 를 헷갈리는 실수가 개발에서 가장 흔하기 때문이다.
유효 구간이 `min ~ max` 라면 **min-1, min, max, max+1** 네 점을 본다.

### 적용 — FR-01-3 비밀번호 길이 (8 ~ 20)

```
        7           8                          20          21
   ─────┼───────────┼──────────────────────────┼───────────┼─────
        │           └──────── 유 효 ───────────┘           │
     무효                                                무효
```

| TC ID | 입력 길이 | 위치 | 기대 | 실제 | 판정 |
|---|---:|---|---|---|---|
| TC-API-SIGNUP-003 | 7 | min-1 | 400 | 400 | Pass |
| TC-API-SIGNUP-004 | 8 | min | 201 | 201 | Pass |
| TC-API-SIGNUP-005 | 20 | max | 201 | 201 | Pass |
| TC-API-SIGNUP-006 | 21 | max+1 | 400 | **201** | **Fail → BUG-001** |

> **여기가 핵심이다.** 개발자는 `if (pw.length < 8)` 만 썼다.
> 하한 3개는 다 통과하지만 상한 하나에서 무너진다.
> "min-1, min, max, max+1" 을 기계적으로 적용하지 않았다면 놓쳤을 결함이다.

### 적용 — 나머지 경계

| 요구사항 | 유효구간 | 검증한 값 | 결과 |
|---|---|---|---|
| FR-01-5 나이 | 14 ~ 120 | 13 / 14 / 120 / **121** | 121에서 **BUG-002** |
| FR-04 size | 1 ~ 50 | **0** / 1 / 50 / 51 | 0에서 **BUG-006** |
| FR-04 page | 1 이상 | 0 / 1 / -1 | Pass |
| FR-06-2 수량 | 1 ~ 99 | **0** / 1 / 99 / 100 | 0에서 **BUG-008** |
| FR-09-3 쿠폰 최소금액 | 30,000 이상 | 14,000 / **30,000** / 42,000 | 30,000에서 **BUG-011** |

**경계값 분석 하나로 결함 5건을 잡았다.** 전체 15건 중 1/3이다.

## 3. 결정표 테스트 (Decision Table Testing)

### 원리
조건이 여러 개 얽혀 결과가 갈릴 때 쓴다. 조건 5개면 조합은 2⁵ = 32가지지만,
앞 조건에서 걸러지면 뒤 조건은 볼 필요가 없다(무관, `-`). 이걸 정리하면 규칙 6개로 줄어든다.

### 적용 — FR-09 주문 처리

| 조건 | R1 | R2 | R3 | R4 | R5 | R6 |
|---|:-:|:-:|:-:|:-:|:-:|:-:|
| C1 장바구니가 비어있음 | **Y** | N | N | N | N | N |
| C2 쿠폰 코드 입력됨 | - | **N** | Y | Y | Y | Y |
| C3 쿠폰이 존재함 | - | - | **N** | Y | Y | Y |
| C4 유효기간 내 | - | - | - | **N** | Y | Y |
| C5 주문금액 ≥ 최소주문금액 | - | - | - | - | **N** | **Y** |
| **결과** | 400<br>EMPTY_CART | 201<br>정가 | 404<br>COUPON_NOT_FOUND | 400<br>COUPON_EXPIRED | 400<br>COUPON_MIN_AMOUNT | 201<br>할인 적용 |
| **TC ID** | ORDER-R1 | ORDER-R2 | ORDER-R3 | ORDER-R4 | ORDER-R5 | ORDER-R6 |
| **결과** | Pass | Pass | Pass | Pass | Pass | Pass |

**32가지 조합 → 6개 테스트케이스.** 이게 결정표를 쓰는 이유다.

### 결정표가 못 잡는 것 — 경계와 계산

결정표는 조건의 Y/N 조합만 본다. "C5가 Y" 라는 건 확인해도
**"정확히 최소금액일 때 Y인가 N인가"** 는 못 본다. 그래서 경계값 분석을 함께 쓴다.

| TC ID | 확인 항목 | 기대 | 실제 | 판정 |
|---|---|---|---|---|
| TC-API-ORDER-001 | 주문금액 = 최소주문금액(30,000원) | 201 할인 적용 | 400 거부 | **BUG-011** |
| TC-API-ORDER-002 | 2,345원 × 10% 할인의 원단위 절사 | 234원 / 2,111원 | 234.5원 / 2,110.5원 | **BUG-012** |
| TC-API-ORDER-003 | 2,345원 주문에 50,000원 할인 | 결제 0원 | **-47,655원** | **BUG-013** |

## 4. 상태 전이 테스트 (State Transition Testing)

### 원리
결과가 "지금 보낸 요청"이 아니라 **"지금까지 보낸 요청의 이력"** 에 좌우될 때 쓴다.
단발 요청 테스트로는 절대 잡히지 않는다.

### 적용 — FR-02-3 계정 잠금

```
     ┌──────────────────── 로그인 성공 (카운트 초기화) ────────────────────┐
     │                                                                     │
     ▼                                                                     │
 [실패 0] ──실패──▶ [실패 1] ──실패──▶ [실패 2] ──실패──▶ [실패 3] ──실패──▶ [실패 4]
                                                                           │
                                                                         실패
                                                                           ▼
                                                                       [잠   금]
                                                                     (해제 API 없음)
```

| 전이 ID | 시작 상태 | 사건 | 도착 상태 | TC ID | 결과 |
|---|---|---|---|---|---|
| T1 | 실패 0 | 로그인 실패 | 실패 1 | TC-API-LOGIN-002 | Pass |
| T2 | 실패 4 | 로그인 실패 | **잠금** | TC-API-LOGIN-005 | **Fail → BUG-004** |
| T3 | 실패 n | 로그인 성공 | 실패 0 | TC-API-LOGIN-004 | Pass |
| T4 | 잠금 | 올바른 비밀번호 | 잠금 유지 | TC-API-LOGIN-006 | **Fail → BUG-004** |

T4가 중요하다. **"올바른 비밀번호로도 뚫리지 않아야 한다"** 는 조건은
"잠금" 상태를 만든 뒤에만 검증할 수 있다.

### 적용 — 토큰 생명주기

| 전이 | 사건 | 기대 | TC ID | 결과 |
|---|---|---|---|---|
| 미인증 → 인증 | 로그인 | 토큰 발급, 인증 API 200 | TC-API-LOGIN-001 | Pass |
| 인증 → 무효 | 로그아웃 | 토큰 폐기 | TC-API-LOGOUT-001 | Pass |
| 무효 상태에서 사용 | 폐기된 토큰으로 호출 | **401** | TC-API-LOGOUT-003 | **Fail → BUG-005** |

## 5. 오류 추정 (Error Guessing) / 탐색적 테스트

### 원리
기법으로 도출되지 않지만 "개발자가 여기서 실수했을 것 같다"는 경험적 직관을 쓴다.
정형 기법으로 뼈대를 만든 뒤 **마지막에** 얹는다. 이걸 먼저 하면 커버리지에 구멍이 생긴다.

| 기법 | 작성 TC | 검출 결함 | 검출 결함 ID |

| 동등분할 | 19 | 2 | BUG-003, 007 |

**결정표가 결함 0건이라고 낭비였던 건 아니다.**
"정상 경로 6개 조합이 전부 정상 동작한다"는 것을 증명했고, 이게 회귀 테스트의 뼈대가 된다.
결함을 찾는 것과 정상을 보증하는 것은 둘 다 테스트의 목적이다.

> **마지막 두 행을 뒤늦게 넣은 이유.** 처음에는 기법으로 도출한 65건만 적었다.
> 그런데 실제 TC는 107건이라 **42건이 표에서 사라져 있었다.** 기법에서 나오지 않은
> 케이스(무토큰 접근, 정상 동작 회귀, 스키마 계약)도 스위트의 일부다.
> 빼놓으면 "기법이 전부"인 것처럼 보이고, 무엇보다 합계가 맞지 않는다.

## 7. BUG-016 — 경계는 입력값이 아니라 "계산 결과"에도 있다

정답지에 없던 결함이 어떻게 나왔는지 남겨 둔다. 기법 적용의 실제 사례이기 때문이다.

FR-06-4 는 한 문장이지만 조건이 둘이다.

> 이미 담긴 상품이면 수량을 합산한다 **(합산 결과도 FR-06-2/3 규칙을 지켜야 함)**

앞 절반만 검증하는 TC는 이미 있었다(TC-API-CART-010: 2개 + 3개 = 5개). 괄호 안은 비어 있었다.

```
addToCart(99)  → 99는 유효 범위(1~99)   ✅
addToCart(1)   → 1도 유효 범위          ✅
──────────────────────────────────────
합산 결과 100  → 상한 99 초과            ❌ ← 경계는 여기 있다
```

**요청 하나만 놓고 보면 어느 쪽도 경계를 넘지 않는다.** 경계는 두 요청이 합쳐진 뒤에 생긴다.
그래서 단일 요청 테스트로는 영원히 안 잡히고, 상태 전이처럼 **순서가 있는 요청 연속**이 필요하다.

### 여기서 배운 것

| | 내용 |
|---|---|
| 기법은 배타적이지 않다 | "경계값을 **어디에** 적용할 것인가"를 정하는 건 상태 전이의 사고방식이다 |
| 명세는 문장이 아니라 조건 단위로 읽는다 | 괄호·단서절 안에 조건이 하나 더 숨어 있는 경우가 많다 |
| 커버리지 단위를 조심한다 | 요구사항 단위로는 FR-06-4 커버리지가 100%였다. 규칙 단위로는 50%였다 |
