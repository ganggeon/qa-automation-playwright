# 명세 결함 리포트 (Specification Defect Report)

| 항목 | 내용 |
|---|---|
| 대상 문서 | `sut/SPEC.md` — MiniShop 요구사항 명세서 v1.0 |
| 검토 방식 | 정적 테스트(문서 리뷰) — 코드 실행 없이 명세만 읽고 검증 |
| 검토 시점 | 테스트 설계 착수 전 + 설계 도중 발견분 |
| 검출 결함 | **6건** (수정 3건 / 열림 3건) |

---

## 왜 명세부터 검토하는가

테스트는 명세를 기준으로 만든다. 그런데 **그 기준이 틀려 있으면 테스트도 같이 틀린다.**

이 프로젝트는 초기에 이 단계를 건너뛰었고, 그 대가를 실제로 치렀다.

- 주문 응답 스키마에 `createdAt` 을 넣었는데, 그건 명세에 없는 필드였다.
  명세를 확인하지 않고 **실행 결과를 보고 스키마를 맞춘 것**이다 (SPEC-DEF-003).
- 상품 페이징 테스트가 `total === 15` 를 상수로 단언했는데,
  명세에는 상품이 몇 건인지 적혀 있지 않았다 (SPEC-DEF-004).

둘 다 "테스트가 통과"했지만, 통과의 근거가 명세가 아니라 구현이었다.
**결함이 있는 구현을 정답으로 삼는 테스트**는 회귀 안전망이 아니라 결함 고착 장치다.

정적 테스트(리뷰·워크스루)가 동적 테스트보다 앞에 오는 이유가 이것이다.
실행하기 전에 잡는 결함이 가장 싸다.

## SPEC-DEF-001 · 상태코드 규약 표에 `423` 이 빠져 있다 — 수정됨

| 위치 | `SPEC.md` §2.2 상태 코드 규약 / §3 FR-02-3 |
|---|---|

**문제**
§2.2 는 이 시스템이 쓰는 상태코드를 표로 규정한다. 목록은 200·201·204·400·401·403·404·409 다.
그런데 FR-02-3 은 계정 잠금 시 **423 Locked** 를 요구한다. 규약 표에 없는 코드다.

**왜 결함인가**
클라이언트 개발자가 §2.2 만 보고 에러 분기를 짜면 423 을 처리하지 못한다.
"규약 표"라고 선언한 이상 그 표는 완전해야 한다. 예외를 본문에만 두면 표의 의미가 없다.

**조치**: §2.2 에 `리소스가 잠김(계정 잠금 등) | 423` 행을 추가했다.

## SPEC-DEF-002 · `403` 은 정의만 있고 사용하는 API가 없다 — 열림

**문제**
§2.2 는 `권한 없음 | 403` 을 정의한다. 그런데 FR-08-2 는 남의 장바구니 항목 삭제에 대해
**"정보 노출 방지를 위해 403이 아닌 404"** 를 명시한다. 실제로 v1.0 의 어떤 API도 403을 쓰지 않는다.

**왜 결함인가**
쓰지 않는 코드가 규약에 남아 있으면 두 가지가 생긴다.
① 테스터가 "403이 나오는 경로가 어딘가 있겠지"라고 가정하고 헛된 케이스를 만든다.
② 다음 개발자가 인가 실패에 403을 써도 규약 위반이 아니게 되어, 404 정책이 조용히 깨진다.

**질의 사항 (제품 오너 확인 필요)**
- 403 을 규약에서 제거할 것인가, 아니면 "향후 관리자 API용으로 예약"이라고 명시할 것인가?

**임시 조치**: §2.2 에 "v1.0 에서 403을 쓰는 API는 없다"는 주석을 달아 오해를 막았다.
정식 결정은 제품 오너 회신 후 반영한다.

## SPEC-DEF-003 · 주문 성공 응답에 `createdAt` 이 누락돼 있다 — 수정됨

| 위치 | `SPEC.md` FR-09 성공 응답 / FR-10 |
|---|---|

**문제**
FR-09 는 주문 성공 응답을 다음과 같이 규정했다.

```
{ "orderId", "totalPrice", "discount", "finalPrice", "items": [...] }
```

그런데 FR-10 은 주문 내역을 **"최신순"** 으로 반환하라고 요구한다.
정렬 기준이 될 시각 필드가 응답 규격에 없다. 구현은 `createdAt` 을 반환하고 있었다.

**어떻게 발견했는가 (자기 지적)**
이 결함은 리뷰가 아니라 **테스트 코드를 되짚어 보다가** 나왔다.
`test-data/schemas.ts` 의 주문 스키마가 `createdAt` 을 `required` 로 걸고 있었다.
스키마에 `additionalProperties: false` 가 걸려 있으니, 명세대로만 썼다면 테스트는 실패했어야 한다.
**실패를 보고 스키마에 필드를 더한 것** — 즉 명세가 아니라 구현에 맞춘 흔적이었다.

이 프로젝트는 "테스트는 코드가 아니라 명세를 보고 설계한다"를 원칙으로 내걸었다.
그 원칙이 한 곳에서 깨져 있었고, 명세 리뷰를 먼저 했다면 나오지 않았을 일이다.

**조치**: FR-09 응답 규격에 `createdAt`(ISO-8601)을 추가하고, FR-10 정렬 기준임을 명시했다.
아울러 응답에 `userId` 같은 내부 식별자를 포함하지 않는다는 규칙도 함께 적었다.

## SPEC-DEF-004 · 상품 마스터가 명세에 없다 — 수정됨

| 위치 | `SPEC.md` §5 테스트 계정 / 초기 데이터 |
|---|---|

**문제**
§5 는 `상품 초기 재고는 GET /api/products로 확인` 이라고만 적혀 있었다.
즉 **상품이 몇 개인지, 가격이 얼마인지가 명세에 없다.**

**왜 결함인가**
테스트가 "가격 33,000원", "총 15건" 같은 값을 단언하려면 근거가 필요하다.
명세에 없으면 근거는 구현밖에 없다. 실제로 `test-data/minishop.ts` 는
상품 id·가격·재고를 통째로 하드코딩하고 있었고, `TC-API-PROD-009` 는 `total === 15` 를 단언했다.
**구현이 틀렸을 때 그것을 정답으로 삼게 되는 구조**다.

**조치**
- §5 에 상품 마스터 16건을 표로 고정했다.
- 아울러 "건수는 하드코딩하지 말고 조회 결과에서 얻어 쓰라"는 지침을 명시하고,
  `TC-API-PROD-009` 를 `total` 을 먼저 읽어 마지막 페이지를 계산하도록 고쳤다.
  마스터가 늘어도 페이징 **규칙**은 그대로 검증된다.

## SPEC-DEF-005 · "만료 당일" 경계를 검증할 데이터가 없다 — 열림

| 위치 | `SPEC.md` FR-09-4 / 쿠폰 마스터 |
|---|---|

**문제**
FR-09-4 는 `유효기간은 expiresAt 당일 23:59:59까지 사용 가능하다` 로 경계를 명시한다.
그런데 쿠폰 마스터에는 `2099-12-31`(먼 미래) 과 `2020-01-01`(먼 과거) 뿐이다.

**"오늘 만료되는 쿠폰"이 없어 경계 자체를 테스트할 수 없다.**
현재 검증되는 것은 "아주 먼 과거는 거부된다"뿐이고, 정작 결함이 나는 지점인
`expiresAt` 당일 00:00 / 23:59:59 / 익일 00:00 은 전부 미검증이다.

**추가 리스크 (구현 검토 중 발견)**
구현은 만료를 다음과 같이 판정한다.

```js
new Date(`${c.expiresAt}T23:59:59`) < new Date()
```

타임존 지정이 없어 **서버의 로컬 타임존으로 해석**된다. 서버가 UTC냐 KST냐에 따라
같은 쿠폰의 만료 시점이 9시간 달라진다. 명세에도 기준 타임존이 없다.

**질의 사항**
- `23:59:59` 의 기준 타임존은? (KST 고정 / 서버 로컬 / UTC)
- 경계 테스트를 위해 "오늘 만료" 쿠폰을 마스터에 추가하거나,
  `POST /api/_reset` 에 쿠폰 주입 파라미터를 열어줄 수 있는가?

**미조치 사유**: 날짜 기준을 임의로 정하면 명세를 테스터가 창작하는 셈이다.
경계 데이터 설계는 제품 오너 결정 사항이므로 질의로 남긴다.

## SPEC-DEF-006 · 타입 위반 시 응답 규칙이 없다 — 열림

| 위치 | `SPEC.md` §2.2 / FR-05 / FR-06 |
|---|---|

**문제**
§2.2 는 `입력값 검증 실패 = 400` 이라고 규정한다. FR-05 는 `없으면 404` 라고 규정한다.
그렇다면 `GET /api/products/abc` 는 400인가 404인가?

- "abc 는 잘못된 입력" → 400
- "abc 라는 상품은 없다" → 404

둘 다 명세로 정당화된다. FR-06 의 `productId: number` 에 문자열 `"1"` 이 왔을 때도 마찬가지다
(구현은 `Number()` 로 변환해 정상 처리한다).

**왜 결함인가**
명세가 두 해석을 허용하면, 테스터는 결국 **구현을 보고 기대값을 정하게 된다.**
그 순간 그 TC는 회귀 테스트로서의 가치를 잃는다. 무엇을 단언하든 항상 통과하기 때문이다.

현재 `TC-API-PROD-018` 은 404를 기대하고 있는데, 이것은 명세 근거가 아니라 구현 관찰에 가깝다.

**질의 사항**
- 경로 파라미터가 정수로 파싱되지 않을 때: `400 INVALID_PARAM` 인가 `404 NOT_FOUND` 인가?
- 본문 필드의 타입 불일치(`productId: "1"`)를 허용(강제 변환)하는가, 거부하는가?

**미조치 사유**: 위와 같음. 임의 결정 대신 질의로 남기고, 결정이 나오면
`TC-API-PROD-018` 의 기대값에 명세 근거를 붙인다.

## 정리

| 구분 | 건수 | 비고 |
|---|---:|---|
| 수정 완료 | 3 | SPEC-DEF-001, 003, 004 — 명세를 보완하고 관련 TC를 함께 정정 |
| 질의 대기 | 3 | SPEC-DEF-002, 005, 006 — 제품 오너 결정 사항 |

**이 리포트에서 얻은 교훈**

1. **명세 리뷰는 테스트 설계보다 먼저 와야 한다.** SPEC-DEF-003·004 는 테스트를 다 만든 뒤에
   발견됐고, 그래서 테스트 코드까지 되돌려 고쳐야 했다. 순서를 지켰다면 한 번에 끝났을 일이다.
2. **"명세에 안 적혀 있다"는 것 자체가 결함이다.** 적혀 있지 않으면 구현이 기본값이 되고,
   구현은 검증 대상이지 기준이 될 수 없다.
3. **모호한 명세는 임의로 해석하지 말고 질의로 남긴다.** 테스터가 명세를 창작하기 시작하면
   그 테스트가 무엇을 보증하는지 아무도 설명할 수 없게 된다.
