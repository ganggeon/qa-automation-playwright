# A. Critical — 릴리스 차단 (P1)

## BUG-004 · 계정 잠금 기능이 전혀 동작하지 않는다

| 항목 | 내용 |
|---|---|
| **심각도 / 우선순위** | Critical / P1 |
| **위반 요구사항** | FR-02-3 |
| **기능 영역** | 인증 |
| **발견 TC** | TC-API-LOGIN-005, TC-API-LOGIN-006, TC-UI-LOGIN-003 |
| **상태** | New |

### 재현 절차
1. `POST /api/users` 로 신규 계정을 만든다 (`qa_bug004_001@test.com` / `Qa123456`, `age: 30`). 재실행 시 이메일의 끝 번호를 바꾸어 중복 가입을 피한다
2. `POST /api/auth/login` 에 **틀린 비밀번호**로 5회 연속 요청한다
3. 6번째에 **올바른 비밀번호**로 로그인을 시도한다

### 기대 결과
```
HTTP 423 Locked
{ "error": { "code": "ACCOUNT_LOCKED", "message": "..." } }
```

### 실제 결과
```
HTTP 200 OK
{ "token": "tok_7_a1b2c3d4", "user": { "id": 42, "email": "qa_bug004_001@test.com" } }
```

정상 로그인된다. 초기 데이터의 `locked@test.com`(잠금 상태로 생성된 계정)도 그대로 로그인된다.

### 원인 분석
`sut/server.js` 로그인 핸들러에서 실패 횟수는 누적하고 `locked` 플래그도 세우지만,
**로그인 시작 시점에 `user.locked` 를 확인하는 분기가 없다.** 플래그를 쓰기만 하고 읽지 않는다.

### 영향
무차별 대입(Brute Force) 공격에 대한 방어가 전혀 없다. 계정 잠금은 보안 요구사항이므로
"기능이 조금 이상함"이 아니라 **보안 통제 부재**로 취급해야 한다.

### 제안 수정
```js
// 자격증명 확인보다 먼저 검사해야 한다
if (user && user.locked) {
  return fail(res, 423, 'ACCOUNT_LOCKED', '계정이 잠겼습니다. 관리자에게 문의하세요.');
}
```

## BUG-005 · 로그아웃한 토큰이 계속 유효하다

| 항목 | 내용 |
|---|---|
| **심각도 / 우선순위** | Critical / P1 |
| **위반 요구사항** | FR-03-1 |
| **기능 영역** | 인증 |
| **발견 TC** | TC-API-LOGOUT-003 |
| **상태** | New |

### 재현 절차
1. 로그인하여 토큰 `T` 를 받는다
2. `POST /api/auth/logout` (Authorization: Bearer T) → 204 확인
3. 같은 토큰 `T` 로 `GET /api/cart` 를 호출한다

### 기대 결과 / 실제 결과
| | 응답 |
|---|---|
| 기대 | `401 UNAUTHORIZED` |
| 실제 | `200 OK` — 장바구니가 정상 조회됨 |

### 원인 분석
로그아웃 핸들러가 `sessions.delete(req.token)` 를 호출하지 않고 204만 반환한다.
서버는 아무 상태도 바꾸지 않으므로 사실상 **로그아웃이 없는 것과 같다.**

### 영향
공용 PC에서 로그아웃해도 세션이 살아있다. 탈취된 토큰을 무효화할 수단이 없다.

## BUG-013 · 할인액이 주문금액보다 크면 결제금액이 음수가 된다

| 항목 | 내용 |
|---|---|
| **심각도 / 우선순위** | Critical / P1 |
| **위반 요구사항** | FR-09-5 |
| **기능 영역** | 주문/금액 |
| **발견 TC** | TC-API-ORDER-003, TC-UI-E2E-003 |
| **상태** | Fixed → Verified (2026-09-07) |
| **재확인 TC** | TC-API-ORDER-003 (결제금액 0원·할인액 2,345원), TC-UI-E2E-003 (주문 성공 메시지·음수 금액 미노출) |

아래 재현 결과와 영향은 수정 전 기록이다. 두 TC는 2026-09-09 전체 실행에서도 Pass다.

> **주석 (2026-09-16 추가)** — 아래 「기대 결과」의 `discount 2,345 (총액까지만)`은 **이 참고 산출물의 기대값**이며
> 요구사항 명세에는 근거가 없다. FR-09-5가 규정하는 것은 `finalPrice`의 0원 하한까지이고,
> 응답 `discount` 필드의 상한은 명세에 정의돼 있지 않다.
> 그래서 위 「재확인 TC」에 적힌 `TC-API-ORDER-003`의 **할인액 단언은 2026-09-16에 삭제**했다.
> **현재 그 TC가 확인하는 것은 `finalPrice`뿐이다.**
> 할인액 필드의 규칙은 명세 확인 항목으로 올렸다
> → [portfolio-submissions/04-명세검토-추가.md](../portfolio-submissions/04-명세검토-추가.md) (SPEC-DEF-007).
> 본문은 참고 산출물이라 그대로 둔다.

### 재현 절차 (수정 전)
1. 로그인 후 `북마크 세트`(2,345원) 1개를 장바구니에 담는다
2. `POST /api/orders` 에 `{ "couponCode": "BIG50000" }` (50,000원 할인)

### 기대 결과 / 실제 결과
| 항목 | 기대 | 실제 |
|---|---:|---:|
| totalPrice | 2,345 | 2,345 |
| discount | 2,345 (총액까지만) | 50,000 |
| **finalPrice** | **0** | **-47,655** |

수정 전에는 UI에서도 `주문이 완료되었습니다. 주문번호 5 / 결제금액 -47,655원` 이 그대로 노출됐다.

### 영향
수정 전에는 결제 연동 시 음수 금액으로 인한 정산 오류나 금전적 손실 위험이 있었다.
MiniShop의 결제 연동은 미구현이므로 실제 지급·손실이 발생한 것은 아니다.

### 제안 수정
```js
const discount = Math.min(rawDiscount, view.totalPrice);
const finalPrice = Math.max(0, view.totalPrice - discount);
```

2. 해당 상품을 **10개** 장바구니에 담는다

### 기대 결과 / 실제 결과

  현재 스키마 계약 검증으로 드러난 결함은 BUG-008 1건이다(TC-API-CART-006의 장바구니 응답 검증).

### 참고
BUG-009(담기 시점 재고 미확인)와 원인은 같은 계열이지만 **수정 위치가 다르다.**
담기에서 막아도 주문 시점에 재고가 줄어 있을 수 있으므로 **주문 시점 검증이 반드시 필요하다.**
두 곳 모두 수정해야 한다.

## BUG-015 · 상품명이 이스케이프 없이 렌더링된다 (XSS 위험)

| 항목 | 내용 |
|---|---|
| **심각도 / 우선순위** | Critical / P1 |
| **위반 요구사항** | UI-01 |
| **기능 영역** | 출력 인코딩 / 보안 |
| **발견 TC** | TC-UI-PROD-002, TC-UI-PROD-003 |
| **상태** | New |

### 재현 절차
1. 로그인 후 상품 목록 화면(`/#/products`)으로 이동한다
2. 상품 ID 4 (`HTML <div> 완전정복`) 의 상품명 표시를 확인한다

### 기대 결과 / 실제 결과
| | 화면 표시 | DOM |
|---|---|---|
| 기대 | `HTML <div> 완전정복` | `<td>HTML &lt;div&gt; 완전정복</td>` |
| 실제 | `HTML  완전정복` (태그가 사라짐) | `<td>HTML <div> 완전정복</div></td>` |

### 원인 분석
`sut/public/index.html` 의 `loadProducts()` 가 서버 데이터를 문자열로 이어붙여
`innerHTML` 에 대입한다. 데이터가 **마크업으로 해석**된다.

### 영향
- **표시 오류**: 특수문자가 포함된 상품명이 잘못 보인다 (즉시 확인 가능한 증상)
- **보안**: 상품명 데이터가 DOM 요소로 해석되므로 XSS 위험이 있다.
  테스트가 확인한 범위는 `<div>` 요소 생성까지이며, 스크립트 실행이나 토큰 탈취는 실증하지 않았다.

### 제안 수정
`innerHTML` 문자열 조립 대신 `textContent` 로 값을 넣거나, 삽입 전에 `<`, `>`, `&`, `"` 를 이스케이프한다.

**재현**

  A의 데이터 삭제를 입증하지 않는다.

**원인**: `discount = (totalPrice * value) / 100` — `Math.floor()` 가 없다.
**영향**: 원화는 소수점 단위가 없다. PG 연동 시 금액 불일치로 결제가 거부되거나
반올림 처리가 시스템마다 달라져 정산 차이가 누적된다.

## BUG-016 · 장바구니 합산 시 수량 상한을 다시 검사하지 않는다 ★ 정답지에 없던 결함

| 항목 | 내용 |
|---|---|
| **심각도 / 우선순위** | Major / P2 |
| **위반 요구사항** | FR-06-4 (및 그 결과로 FR-06-2) |
| **기능 영역** | 장바구니 |
| **발견 TC** | TC-API-CART-018 |
| **발견 기법** | 경계값 분석 — "합산 **이후**의 값"에도 경계가 있다 |
| **상태** | New |

### 발견 경위

**학습 시작 전(2026-08-03) Claude·Codex의 사전 검토에서 발견됐다.**
의도적 주입 목록에는 없던 결함이며, 아래는 당시 검토에서 확인한 조건과 테스트 공백이다.

FR-06-4 는 한 문장이지만 조건이 두 개다.

> 이미 담긴 상품이면 수량을 합산한다 **(합산 결과도 FR-06-2/3 규칙을 지켜야 함)**

앞 절반(합산된다)만 검증하는 TC는 이미 있었다(TC-API-CART-010). 괄호 안의 뒷 절반은
기존 TC에서 검증되지 않았다. **경계는 입력값에만 있는 게 아니라 계산 결과에도 있다.**

### 재현 절차

1. 로그인 후 `연습장 100매`(id 16, 재고 999)를 **99개** 담는다 → `201`
2. 같은 상품을 **1개** 더 담는다 (합산하면 100개)

### 기대 결과 / 실제 결과

| | 응답 | 장바구니 수량 |
|---|---|---:|
| 기대 | `400 INVALID_QTY` | 99 (변화 없음) |
| 실제 | **`201 Created`** | **100** |

재고 999짜리 전용 상품을 쓰므로 재고 규칙(FR-06-3)에는 걸리지 않는다.
즉 여기서 드러나는 위반은 **오직 수량 상한(FR-06-2)** 하나다.

### 원인 분석

```js
// sut/server.js — 담기 핸들러
if (!Number.isInteger(qty) || qty > 99) { ... }   // ← 요청값 하나만 검사
...
if (exist) exist.qty += qty;                      // ← 합산 결과는 재검사하지 않음
```

검증이 **요청 시점**에만 걸려 있고 **상태 변경 시점**에는 없다.
BUG-008은 요청 수량의 하한 검사가 빠진 것이고,
BUG-016은 요청값의 상한을 검사하면서 **합산 결과에는 같은 검사를 적용하지 않은 것**이다.

### 영향

수량 상한을 두는 이유(1인당 구매 제한, 재고 확보, 어뷰징 방지)가 무력화된다.
요청을 여러 번 나눠 보내면 상한을 얼마든지 우회할 수 있고, 재고 검증이
수정되더라도 이 경로는 그대로 남는다.

### 제안 수정

```js
if (!Number.isInteger(qty) || qty < 1 || qty > 99) {
  return fail(res, 400, 'INVALID_QTY', '요청 수량은 1~99 범위의 정수여야 합니다.');
}
const merged = (exist?.qty ?? 0) + qty;
if (!Number.isInteger(merged) || merged < 1 || merged > 99) {
  return fail(res, 400, 'INVALID_QTY', '수량은 1 이상 99 이하의 정수여야 합니다.');
}
if (merged > product.stock) {
  return fail(res, 409, 'OUT_OF_STOCK', '재고가 부족합니다.');
}
```

> **이 사례의 시사점.** Claude·Codex의 사전 검토에서 의도적 주입 목록 밖의 결함도 발견됐다.
> 주입 결함 15건의 검출률만으로는 전체 품질이나 학습자의 독립적인 설계 역량을 판단할 수 없다.
> BUG-016은 요청값뿐 아니라 **상태 변경 후의 계산 결과도 검증해야 한다**는 사례다.

# D. 회귀 방지 방안

각 결함마다 대응하는 자동화 테스트케이스가 이미 존재하며,
미수정 항목은 `test.fail()` 로 **"알려진 실패"** 라 표시해 두었다.
BUG-013의 재확인 TC는 해당 마킹 없이 통과한다.

```ts
test('TC-API-ORDER-001 | [경계값] 주문금액이 최소주문금액과 정확히 같으면 쿠폰이 적용된다', async ({ shop }) => {
  test.fail(true, 'BUG-011: 최소주문금액 비교를 초과(>)로 하여 정확히 같은 금액이 거부된다');
  ...
});
```

이 방식의 이점

1. **CI가 초록불로 유지된다** — 미수정 결함 때문에 매일 빨간불이 뜨면 팀이 실패에 무뎌진다
2. **결함이 수정되면 자동으로 알려준다** — 수정 후 테스트가 통과하면
   Playwright가 `Expected to fail, but passed` 로 실패시킨다. 마킹을 지우라는 신호다
3. **결함 목록이 코드에 산다** — 별도 문서와 코드가 따로 놀지 않는다

수정 완료 후 절차
1. `test.fail()` 한 줄 삭제
2. 전체 176건 재실행 (`npx playwright test`, 또는 `npm run test:all`)
3. 통과하면 결함 상태를 `Verified → Closed` 로 변경
