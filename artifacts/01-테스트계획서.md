| 작성자 | QA |

## 1. 목적

MiniShop v1.0이 요구사항 명세(SPEC.md)를 충족하는지 확인하고, 출시 가능 여부를
판단할 근거를 제공한다. 부수적으로 회귀 테스트 자산(자동화 스위트)을 구축한다.

## 2. 테스트 범위

### 2.1 포함 (In Scope)

| 구분 | 대상 | 테스트 레벨 |
|---|---|---|
| 회원 | 가입(FR-01), 로그인(FR-02), 로그아웃(FR-03) | API, UI |
| 상품 | 목록/검색/페이징(FR-04), 상세(FR-05) | API, UI |
| 장바구니 | 담기(FR-06), 조회(FR-07), 삭제(FR-08) | API, UI |
| 주문 | 주문·쿠폰·재고(FR-09), 내역(FR-10) | API, UI |
| 화면 | 표시 규칙(UI-01~03) | UI |
| 비기능 | 인증/인가, 출력 인코딩, 응답 시간 | API, UI |

### 2.2 제외 (Out of Scope)

| 제외 항목 | 사유 |
|---|---|
| 성능/부하 테스트 | 별도 도구·환경 필요. 본 릴리스 범위 밖 |
| 결제 연동(PG) | 미구현 기능 |
| 다국어/접근성 | v1.0 요구사항에 없음 |
| 모바일 실기기 | 데스크톱 웹만 지원하는 릴리스 |

## 3. 테스트 접근 방법

### 3.1 테스트 피라미드

```
        ▲  E2E (UI)         3건   — 사용자 핵심 경로만. 느리고 잘 깨짐
       ╱ ╲
      ╱   ╲ UI 통합        15건   — 화면 표시 규칙, 오류 노출
     ╱─────╲
    ╱       ╲ API          89건   — 경우의 수 대부분을 여기서 커버
   ╱─────────╲
```
(UI 18건은 Chromium·Firefox·WebKit 3종에서 각각 실행 → 54건)

같은 검증을 UI에서 반복하지 않는다. 예를 들어 "비밀번호 8자 경계"는 API에서
검증하고, UI에서는 "실패 시 오류 메시지가 화면에 뜨는가"만 본다.
비용은 1/10인데 커버리지는 같다.

### 3.2 적용 테스트 설계 기법

| 기법 | 적용 대상 |
|---|---|
| 동등분할 | 이메일 형식, 비밀번호 구성, 검색어, 계정 유형 |
| 경계값 분석 | 비밀번호 길이(8/20), 나이(14/120), 수량(1/99), size(1/50), 쿠폰 최소금액 |
| 결정표 | 주문 처리(조건 5개 → 규칙 6개) |
| 상태 전이 | 로그인 실패 누적 → 계정 잠금, 토큰 생명주기 |
| 오류 추정 | 재고 음수, 음수 결제금액, 소수점 잔여, 남의 리소스 접근, 타 회원 데이터 격리 |
| 정적 테스트 (명세 리뷰) | 상태코드 규약 완전성, 응답 규격 누락, 초기 데이터 미정의, 경계 검증 가능성 |

상세 도출 과정: [02-테스트케이스-명세.md](02-테스트케이스-명세.md)

## 4. 테스트 환경

| 구분 | 내용 |
|---|---|
| SUT | `http://localhost:4010` (Node.js 22 + Express) |
| 자동화 도구 | Playwright 1.5x (TypeScript) |
| API 도구 | Playwright APIRequestContext, Postman/Newman |
| 스키마 검증 | Ajv (JSON Schema Draft-07) |
| 브라우저 | Chromium(기준), Firefox, WebKit |
| CI | GitHub Actions (push / PR / 매일 03:00 KST) |

### 4.1 테스트 데이터 관리

- 계정: **테스트마다 신규 계정을 생성**하여 격리한다. 공용 계정을 쓰면 병렬 실행 시 서로의 상태를 오염시킨다.
- 재고: 전역 상태이므로 **테스트별 전용 상품**을 지정해 소유권을 나눈다 (`test-data/minishop.ts`).
- 초기화: 실행 시작 시 `POST /api/_reset` 1회. 테스트마다 초기화하지 않는다(병렬 실행과 충돌).

## 5. 진입 / 종료 조건

### 5.1 진입 조건 (Entry Criteria)
- 요구사항 명세서가 확정되어 있다
- **명세에 대한 정적 테스트(리뷰)가 완료되어 있다** — 기준 문서가 틀리면 테스트도 같이 틀린다.
  명세 결함은 `06-명세결함리포트.md` 로 별도 관리하고, 해석이 갈리는 항목은
  임의 판단하지 않고 질의로 남긴다
- SUT가 테스트 환경에 배포되어 기동된다
- 스모크 테스트(로그인 → 상품조회)가 통과한다

### 5.2 종료 조건 (Exit Criteria)

| 조건 | 기준 |
|---|---|
| 계획한 테스트케이스 수행률 | 100% |
| Critical / Major 결함 | 잔존 0건 |
| Minor 결함 | 릴리스 노트에 명시 후 차기 반영 가능 |
| 자동화 스위트 | 미해결 결함을 제외하고 전부 통과 |
| 회귀 테스트 | 결함 수정 후 전체 스위트 재실행 통과 |

## 6. 결함 관리

### 6.1 심각도(Severity) 기준

| 등급 | 정의 | 예 |
|---|---|---|
| Critical | 데이터 손상, 금전적 손실, 보안 침해. 우회 불가 | 음수 결제금액, 재고 음수, 계정 잠금 무력화 |
| Major | 주요 기능이 명세대로 동작하지 않음. 우회 어려움 | 품절 상품 주문 가능, 쿠폰 미적용 |
| Minor | 기능은 동작하나 명세와 다름. 우회 가능 | 검색 대소문자 구분, 응답 코드 불일치 |
| Trivial | 사용에 지장 없는 표기·문구 | 오탈자 |

### 6.2 우선순위(Priority) 기준
- **P1**: 릴리스 차단. 즉시 수정
- **P2**: 이번 릴리스 내 수정
- **P3**: 차기 릴리스 반영

> 심각도와 우선순위는 **다르다.** 로그인 화면 로고 오탈자는 Trivial이지만
> 대외 발표 전날이면 P1일 수 있다.

### 6.3 결함 생명주기
```
신규(New) → 할당(Assigned) → 수정(Fixed) → 재확인(Verified) → 종료(Closed)
                                   ↓ 재현됨
                              재오픈(Reopened)
```

## 9. 리스크

| 리스크 | 영향 | 대응 |
|---|---|---|
| 외부 데모 사이트(SauceDemo, restful-booker) 변경/장애 | 테스트 실패로 오인 | 별도 CI Job으로 분리 + `continue-on-error` |
| 병렬 실행으로 인한 테스트 간섭 | 간헐 실패(Flaky) | 계정 격리 + 상품 소유권 지정 + 재고는 변화량으로 검증 |
| 미수정 결함이 계속 실패로 표시됨 | 실패에 무뎌짐 | `test.fail()`로 알려진 결함 마킹. 수정되면 자동으로 알림 |
| SUT가 메모리 상태를 사용 | 재실행 시 상태 누적 | 실행 시작 시 1회 초기화 + 상대 검증 |
